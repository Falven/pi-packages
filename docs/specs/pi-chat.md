## Problem Statement

Pi users need to follow current activity, inspect earlier agent activity, and find retained conversation content without reading an unbroken stream of commands, thoughts, and output. Existing extensions provide parts of this experience, but their overlapping rendering and input changes can conflict.

The chat view groups consecutive activity and collapses earlier agent activity while keeping the final response visible. Pi's native Hide thinking choice controls whether thoughts appear inline. It must operate inside Pi's terminal interface, preserve the original conversation, and reuse native content presentation. It must not require a separate application, service, Pi fork, or modifications to Pi's installed source.

Generic execution titles and operation counts do not identify the agent activity hidden inside a render group. Opening a group can still leave commands indistinguishable, and a single tool call can change several files or run several commands while exposing only one shared disclosure. Pi's default collapsed renderers can also reveal previews and errors before the user chooses to inspect an operation. Users need consistent item summaries and independent activity bodies across built-ins, the core toolset, and other extensions.

## Solution

Build `pi-chat`, one extension that owns the main chat view in Pi's fullscreen mode. A chat view is the primary conversation surface alongside the composer; a transcript is a separate history-reading overlay and is outside this package's scope.

The extension composes Pi's existing message components and activity body components into occurrence-aware agent activities, render-group disclosures, and native thought Markdown in ordinary chat flow. Final responses appear after their agent activity and remain visible when that history closes. Expanded render groups expose every activity item in ordinary conversation flow, and opened bodies use native preview or expanded output sizes according to their own state without a group or body height cap; visible thoughts have no separate header, viewport, or disclosure. Hide thinking removes thought rows completely while retaining their source and native working labels. Source Find temporarily reveals only its selected hidden thought occurrence without changing Hide thinking.

Tool adapters owned by pi-chat translate built-in and extension facts into a common activity-item model. The collapsed render group shows `>` and a group summary such as `Edited files, ran commands`. Opening it exposes individual activity items with their existing disclosure choices. New groups and items inherit Pi’s native global expansion state, which defaults to collapsed. A collapsed activity item contains only `>` and a specific item summary, such as `Ran git diff --check` or `Edited GLOSSARY.md +8 -1`. Opening one row reveals Pi's native output control in its current state, showing the collapsed preview by default. Clicking that control expands or collapses its output independently of the item and its siblings. Closing and reopening an item or ancestor preserves the native output choice. Built-ins use native renderers and extensions use Pi's generic default rendering in both states. Pi's preview belongs inside an open item; an extension's custom renderer does not satisfy this default rendering boundary.

One tool call can produce several operations. Commands in an execution cell and files changed by one patch receive separate rows. The cell's own output or error receives one separate execution activity item when it does not belong to a child operation; empty entries and duplicated child output are omitted. Child status remains independent of the cell's status. Existing source binding, standalone-notice ordering, agent activity collapsing, and final-response behavior remain in force.

Pi continues to own conversation data, execution, effective Markdown, default activity-body rendering, the composer and surrounding dock, themes, terminal protocols, and final painting. One isolated host adapter supplies the private runtime access required for exact native component identity and composition. Pi 1.1.0 and later are the primary target. Compatibility depends on required capabilities rather than a version string; real-host tests also retain coverage for Pi 1.0.2. Regular mode and the history printed on exit retain native behavior.

## Implementation Decisions

- **Package and ownership.** Implement pi-chat as one extension with internal modules for the host adapter, tool adapters, activity-item and occurrence indexing, group summaries, relationships, disclosure policy, layout and interaction, and source search. These modules share one lifecycle and source identity model. All tool-to-activity-item adapters and their registry belong inside pi-chat. Providers expose facts; they do not own chat summaries or grouping. Do not publish a shared adapter framework or require companion packages as runtime dependencies.

- **Native content boundary.** Pi remains the canonical owner of messages, session entries, model context, execution, and the native event reducer. Borrow native message components and use Pi's default activity-body rendering for activity-item projections. Preserving an extension's custom renderer chain is superseded for those activity bodies. Never insert markers into message content, replace messages for rendering identity, rerun tools, or maintain a second joined conversation buffer. Render-only source references and native rendered-line caches do not become conversation history.

- **Runtime compatibility.** Use one in-process adapter as the accepted exception to the repository's usual public-extension-only boundary. Check required functions when acquiring hooks and preserve native chat-root ownership. Missing hooks must produce an error naming the function; missing hooks or competing ownership prevent activation, restoring changes made during a failed attachment. Do not gate on Pi's version string. Target Pi 1.1.0 and later, validate against 1.1.0, and retain secondary coverage for 1.0.2; function presence alone does not prove behavioral compatibility with future releases. Prefer public APIs when available, including settlement cancellation and selection reset, retaining private fallbacks only where the tested runtimes require them.

- **Host acquisition and root replacement.** Capture the actual `InteractiveMode` through a scoped observation of the native widget method reached by `ctx.ui.setWidget`; restore the prototype descriptor immediately. Verify TUI mode and the same session manager. Save and replace `fullscreenLayoutRoot`, reusing the exact pending-message, status, widget, editor, and footer containers. Leave the native document, chat container, and event reducer alive. Use the original document in regular mode and for history printed on exit.

- **Reload bootstrap.** Native history can be constructed before `session_start` on reload or session replacement. During extension initialization, temporarily observe `renderSessionEntries`. Recognize the owning runner by the function identity of the extension's registered relationship-entry renderer, install the instance adapter before history construction, and restore the prototype. Disarm any remaining observer at `session_start`; use widget acquisition for initial TUI startup. Support the normal Pi CLI lifecycle. Abandoned extension discovery through custom SDK loaders is outside this lifecycle contract.

- **History assembly and binding.** Call native `renderSessionEntries` with a shallow array referencing original entries. Observe its entry-local `flatMap` projection on that array to associate actual projected items with their source entry and item ordinal, leaving entries and messages untouched. Pass the items to the original `renderSessionItems` through a scoped iterator so association remains available during native tool, notice, and message construction. Preserve native selection reset, projection rules, and options; restore the scoped method in `finally` and fail explicitly if association is lost. This retains a dependency on the native `flatMap`-then-`renderSessionItems` path. Observe insertion and removal paths. Associate each original native custom-entry component with its actual source entry whether Pi appends it or inserts it directly before a streaming assistant component. Cover live construction and replay through the same adapter; an append-only observer is insufficient. Source identity alone does not establish agent activity membership. Keep unpersisted native notices by component identity and insertion position. Do not trigger an extra destructive history rebuild.

- **Native component association.** Associate assistant content parts and adjacent thinking runs with the children produced by native construction, including its trimming and thinking aggregation. Rebind those references after native assistant updates recreate children. Preserve native semantic terminal markers. Bind activity items to stable operation identities and their original call, result, entry, and content-part references. Reuse suitable native activity-body components and create default activity-body components for split operations as needed; do not duplicate an extension's active custom renderer. Do not display both projected operations and their original aggregate card. Images retain one visible owner.

- **Operation facts and lifecycle.** Adapters normalize public tool events, effective arguments, processed results, and reliable retained provider facts. The core-tool adapter consumes the provider's documented live updates through Pi's event bus and its retained result/activity facts. Provider-specific decoding stays in that adapter; the grouping and disclosure modules consume only the common model. Stable source-scoped identities distinguish commands, per-file patch operations, and the cell's own execution activity item. Preserve initial operation order and update existing rows in place through yields, waits, late completion, and later prompts. A parent return, failure, or agent end does not establish a child's outcome. Routine activity records remain invisible and do not become group boundaries.

- **User-message layout.** In fullscreen chat, render the existing native `UserMessageComponent` at the full chat width, retaining its full-width themed background bar. Align its rendered content as one block to the right with native right padding while preserving relative Markdown indentation and layout. Use the native blank padding row to fill the bar background during cell-aware composition. Keep OSC 133 markers at the row prefix, translate child pointer coordinates, and let search and selection use the displayed aligned rows. Copying selected user text excludes the existing output-padding gutters and added left layout margin while retaining content indentation; do not inset the native component again. Preserve original message data, regular mode, and printed-exit rendering.

- **Conversation gutters.** Reuse the current native `outputPad` on both sides of the whole conversation viewport, including messages, disclosure headers, and activity bodies. Count it once; add no columns, minimum gutter, second inset, or setting. Zero padding means no gutter. Wheel input over this space scrolls the conversation directly before a child can consume it. Recompute horizontal bounds with padding and content-width changes. Keep the native scrollbar region and its pointer priority, including at a gutter edge. Composer, dock, and overlays retain their geometry and priority.

- **Native presentation settings.** Pi remains the source of settings, defaults, and allowed values. Read its current `outputPad` and native transcript scrollbar mode before layout; do not duplicate settings or introduce new flags. Use native components for render-group and agent-activity headers with the current padding, including the agent activity divider. Pi updates its live message and tool presenters; propagate padding changes through available native setters on detached historical presenters. Use native scrollbar style callbacks and `getContentWidth()` before measuring or aligning rows. Native `always` reserves its gutter, `auto` retains native overlay and hiding behavior, and `hidden` leaves it absent. Reuse native track clicks, thumb dragging, hover, timing, and painting. The older Pi 1.0.2 tool presenter has a fixed inset and its settings path can rebuild history; preserve those native behaviors rather than adding private compatibility code.

- **Absent historical content.** Materialize rows omitted by Pi's compaction-aware display projection through native factories into a detached destination, without populating editor history or clearing live pending-tool state. Use historical tool initialization without execution-start behavior or speculative edit previews. For otherwise-hidden thought bodies, use native assistant construction with a render-only array referencing the original thought blocks and the current Markdown environment. Reuse these owned historical presenters until a relevant invalidation or lifecycle change requires replacement.

- **Occurrence identity.** Assign a stable presentation handle to each source occurrence. A live handle points to the current live message and content part; after native persistence, promote that same handle to its committed entry and part reference. Use source entry and projected item ordinal where one entry yields several native items. Content equality, hashes, callback order, timestamps, and screen position do not determine occurrence identity. Equal progress and final text therefore remain independently addressable.

- **Incremental indexing.** Index the raw active branch once, including retained originals omitted by compaction. Reconcile appended entries and changed live occurrences incrementally, and rebase on session or branch changes. Retain references, classifications, revisions, and relationships rather than copied message bodies. Scrolling and collapsing consume the existing index; they do not scan history or hash unchanged content. No hashing dependency is required by this design.

- **Actual input delivery.** Observe the message objects passed to the particular agent's initial prompt operation and returned by its steering and follow-up queue drains. Preserve calls and return values unchanged. Certify delivery only when the corresponding user message starts. An agent listener ordered after native session persistence joins delivered objects to committed entries. Submission intent, queued text, or an input-handler snapshot cannot establish delivery, including when queued prompts contain identical text.

- **Agent activity relationships.** A delivered steering message continues the current agent activity and forms a user boundary between render groups. Every user message remains visible when agent activity is collapsed. Expanding agent activity restores agent activity around the same user occurrences in source order, without duplication. Derive final-response spacing from the last retained visible row, including an intervening notice, rather than an earlier user row. When that last row is a user-message bar, keep one neutral blank line before the final response; reuse native spacing rather than adding a second gap. A delivered follow-up starts a new turn with its own agent activity and answer relationship. An assistant message boundary or agent-loop boundary alone does not begin new agent activity.

- **Standalone extension notices.** A positively identified standalone extension notice without established agent activity membership remains visible while the surrounding known agent activity composes with its selected final response. Keep activity within the turn, retained user rows, and notices in one native-ordered sequence. Closing agent activity hides only its known activity within the turn; reopening it restores those activities around the same retained rows without duplication. Visible notices continue to split render groups. A notice alone does not create an empty agent activity disclosure. Preserve actual request, history, and compaction boundaries, stop at agent activity for a different known turn or an unidentified message row, and never move a notice after the selected final response ahead of it. Do not infer notice ownership from arrival time, the current request, or matching text. This treatment does not make every native status or unknown row transparent to agent activity composition.

- **Relationship persistence.** Append only minimal native custom session entries for certified delivery, agent activity, and final-phase relationships needed on replay. They contain classifications and source references, never copied conversation text or disclosure choices, and remain outside model context. Interpret references within the session journal so copied history in a fork can be rebased. Persist established facts, not guesses that attempt to repair missing provenance.

- **Historical uncertainty.** When historical delivery or phase provenance is unavailable, leave only the uncertain agent activity relationships expanded. Preserve known ordering, tool disclosures, inline thoughts, and search. Do not invent boundaries, phase labels, or explanatory chat messages. Missing historical provenance is distinct from an unsupported host structure, which prevents adapter activation.

- **Activity eligibility and summaries.** Every tool provider participates through the adapter path, including unmodified extensions through the fallback. Consecutive activity items and nonempty execution activity items accumulate across assistant messages until visible commentary, visible thoughts, user rows, another standalone non-tool item, or an explicit boundary intervenes. A tool-call or execution-cell boundary alone does not separate groups. Omitted reasoning does not split activity. Group eligibility does not depend on successful classification. The group-summary module derives group summaries from operation types and reliable facts, independent of provider names and renderer content.

- **Group summary lifecycle.** Compose type summaries in a stable order, retaining the established loaded-tool, generic-tool, edit, read, and command ordering and summarizing execution activity items where present. Use sentence-initial case for the first segment, lowercase for later segments, and commas between segments. Identity-based counting and existing distinct-target rules determine singular or plural wording without printing an operation count as a substitute for the description. Unknown activity items use a useful tool-name fallback without invented semantics; their group summary uses the generic operation type. Running operations change the relevant type wording while the group still summarizes all included types; one activity item's specific summary never replaces the group summary. Observe actual lifecycle facts, including continuing agent activity after a parent returns. A missing result alone does not prove running agent activity. Ordinary scrolling reads cached summaries; the thought working-message slot remains separate.

- **Render group lifecycle.** Every render group keeps its outer disclosure, including a settled group with one operation or execution activity item. New groups and items inherit Pi’s current global expansion state, normally collapsed, including while executing. A group stays active while additional consecutive operations can still join; completion of one operation alone does not settle it. Preserve manual choices through growth, completion, ordinary failure, and cancellation until an explicit individual or global toggle changes them. A collapsed group shows only `>` and its group summary. Opening it exposes every activity item in conversation flow while preserving existing child choices. One call changing several files or running several commands produces several rows when reliable operation facts support that decomposition.

- **Disclosure interaction and lifetime.** Follow Pi’s configured `app.tools.expand` action and native global expansion flag; Ctrl+O is only its default, never a hard-coded additional binding. The action expands or collapses all available agent activity, render-group, and activity-item disclosures together with native output expansion. New groups and items inherit that flag. Individual ancestor toggles preserve descendant choices; the next explicit global action sets all available levels. Store manual choices in memory, retaining them through redraw, growth, updates, completion, and resize while their disclosure exists. Reset them on application restart or extension reload. Do not store choices in conversation content or relationship entries, and do not change Hide thinking or final-response visibility.

- **Adapter organization and selection.** Keep named built-in, core-tool, and generic fallback adapter modules behind one explicit local registry. Isolate provider-specific interpretation in those modules and maintain the supported mappings, selection order, required facts, and fallback behavior together in this specification's operator catalog. An operator changes or adds a mapping in the package without modifying chat layout or the tool provider. Select specific adapters using reliable tool identity and provenance, not a familiar tool name alone. A replacement or unknown tool falls back safely unless an adapter has sufficient facts. No third-party tool is required to implement a new protocol to remain usable.

- **Common activity-item description.** Describe an activity item with stable identity, originating source references, order, operation type, action/target facts, actual lifecycle status, optional verified change statistics, and an activity-body payload or reference with explicit availability. Adapters translate facts into this description; shared chat formatting produces item summaries and aggregates group summaries. Tool-call, execution-cell, and process identities retain ownership and continuation relationships without fixing the number of rows or grouping their disclosures. Splitting a tool call's presentation does not create synthetic model-facing tool calls or session messages.

- **Item disclosure and native output state.** A closed activity item renders only `>` and its specific item summary, with no body, preview, diff, image, omission notice, or error message. Opening it reveals Pi's native output control in its own state, collapsed to a native preview by default. Use native renderers for verified built-ins and generic default rendering for extensions in both preview and expanded states; do not carry forward custom extension result renderers. Delegate output clicks to Pi so that expanding or collapsing output leaves the item open. Preserve both choices independently through redraw, updates, individual ancestor toggles, and settings reconstruction; retain the existing in-memory/reload lifetime. The configured app.tools.expand action sets item and output states together, and new controls inherit its native flag. Keep the specific command summary while output is a preview; it may shorten when full output is expanded. Do not add another custom control, preview renderer, height limit, setting, or shortcut.

- **Command and edit item summaries.** Share conservative command classification across built-in and extension adapters. Recognize reads, searches, and directory listings only when effective arguments support an unambiguous interpretation; otherwise retain a command-specific item summary such as `Ran git diff --check`. Do not infer actions from orchestration source or rendered output. Built-in editing tools and the core patch tool map to edit operations. A patch can produce one row for each affected file, with only that file's applicable inputs, result, and outcome in its activity body. Show additions and deletions only from verified change data; omit unavailable counts instead of inferring them from requested replacement text or current disk contents. Do not report unattempted or failed changes as successful edits.

- **Execution activity item and attribution.** Preserve a cell's own output or error in one separate execution activity item when the content does not belong to a child operation. Apply the same native global-state inheritance, summary-only collapsed header, default generic expanded activity body, and independent disclosure. Omit empty entries and attributed child-output duplicates. Track producing operation or script ownership explicitly; equal text alone cannot justify dropping genuine script output. A failure before any child starts must still produce an accessible entry, such as `Execution failed`. Successful children remain successful when the script fails. Continuing input, waits, and collection retain their appropriate outcomes without replaying the original command body.

- **Activity-body retention and replay.** Separate compact operation descriptions from bounded activity-body output. Activity-body output limits must not remove known command or file rows, distort group summaries, or replace known outcomes with uncertainty. Mark missing or omitted activity-body content explicitly and explain it only when the relevant row is opened. Reconcile the latest reliable records on the active branch without recreating live resources. Keep older history usable through available original data and honest fallbacks; do not invent missing operations, counts, outcomes, or payloads. Preserve effective hooks and authoritative processed results when accepting live or retained facts.

- **Final-response selection.** Keep provider phase, selected final response, and settled agent activity outcome as separate facts. Associate provider phase evidence with the exact normalized content occurrence, including when several provider items share one assistant message. Remove the selected final occurrence from the agent activity sequence and present it after the agent activity. Never identify it by matching text. Native user and standalone activity ordering remains intact.

- **Agent activity collapse.** Agent activity becomes eligible to collapse automatically as qualifying final-response text starts, subject to explicit individual or global disclosure choices and keep-open choices. A successful completion is not required. Selection and scroll position do not defer automatic collapse. Cancellation, absence of a qualifying final response, or a terminal error that disqualifies that candidate prevents automatic collapse; none overrides an explicit expansion or closure. Render groups retain their independent state unless the global action changes it. Failure alone is not a blanket completed-answer requirement.

- **Agent activity header.** Display `Worked for <minutes>m <seconds>s` followed by `▶` when collapsed or `▼` when expanded. Derive whole elapsed seconds from the delivered-request entry timestamp to the last committed agent activity entry at settlement; while unsettled, use the current redraw time. Do not count queue waiting or restart the duration on reload, and add no timing metadata or timer. Render the summary with the native muted color and a native thin divider below it, both using the current output padding. Leave a neutral blank line above the header and below the divider in both disclosure states. Focus underlines the summary only; the header and divider have no background.

- **Providers without final-phase evidence.** When the provider supplies no usable final-phase information, treat the text of a qualifying terminal assistant message as one final response only after agent activity settles. Do not split its prose into commentary and answer, infer phase from wording, or promise early collapse without evidence. Preserve cancellation and missing-final behavior.

- **Thinking visibility.** Reuse Pi's native `hideThinkingBlock` setting and its existing controls. When true, omit reasoning rows entirely, including placeholders, headers, spacing, and disclosures; group eligible tool calls across omitted thoughts. If reasoning was the only agent activity before a final response, also omit the otherwise-empty Worked disclosure. When false, preserve full inline native thought prose apart from extracted activity headings, and let visible thoughts separate render groups. Apply the same rule to retained and compacted historical reasoning. Preserve canonical source and searchability in either mode. Add no setting or raw-versus-summary distinction; provider and model controls remain Pi's responsibility.

- **Inline thoughts.** When Hide thinking is off, show native thought Markdown at each thought's source-ordered chat occurrence in ordinary flow, apart from extracted activity headings, reusing native renderers and caches. Keep it visible after completion whenever its enclosing agent activity is open. Give thoughts and adjacent render groups visual separation. Thoughts have no separate header, bounded viewport, or keyboard/mouse toggle; whole agent activity collapsing remains independent. Do not move them to a docked widget. Account for the native renderer's adjacent thinking-block aggregation in source mapping.

- **Activity headings.** Treat a standalone bold paragraph anywhere in thinking, including midway through a block, as a transient activity label in Pi's native working indicator in either Hide thinking mode. Use Pi's public `registerMarkdownTransformer` only for assistant-thinking display to omit that paragraph from the native thought body; inline bold emphasis remains ordinary prose. Public `message_update` sets the latest recognized label through `ctx.ui.setWorkingMessage`, and `thinking_end`, `message_end`, and `agent_end` clear this extension's label. Keep original thinking blocks in the native presenter and preserve canonical messages and session history. Add no occurrence-targeting hook, alternate renderer, custom spinner, package, or setting.

- **Conversation flow and anchors.** Maintain source occurrences and disclosures in ordinary conversation flow. An expanded render group exposes every activity item, and a standard expanded body grows to Pi’s native size. Add no shared group viewport, independent body viewport, or height cap. Native tool preview limits and retained-output limits are distinct from display height. The primary native `ScrollView` owns conversation offsets and bounds. Preserve the first visible occurrence and local row when heights change, or follow the end when the conversation was already following. Preserve native child scroll state where the content itself provides it.

- **Layout and native painting.** Allocate the existing dock first, then measure dirty content at its final content width and intersect all logical clips. Register the owned primary `ScrollView` in Pi's layout so native scrollbar geometry and input use the full logical chat height. Its child supplies blank geometry rows and positions the visible intervals between spacers above and below. Each interval remains a native `ScrollView` over original uncropped rows, with its exact visible height and its own scrollbar hidden; these painting windows are not independent user scroll areas. Keep these painting windows at terminal width inside a non-shrinking native `HStack`; the outer content clip excludes any reserved gutter while preserving Pi's full-width image recovery path. Give each occurrence one presentation location. Retain image reservation rows and native image instances. Only the leaf window supplies image content, so Pi performs one image crop, transmission, placement, and terminal diff despite the outer scroll layout.

- **Rendering cost.** Preserve native renderer instances and caches. Use frame-local references to rendered rows so measurement and painting do not render a borrowed component twice. The outer scroll geometry retains one blank string reference per logical display row, resizing only when the height changes; it stores no conversation text or joined rendered transcript. Scrolling changes offsets and requests a redraw without invalidating unchanged Markdown. Add another cache only when all invalidations can be observed and measurements justify it. Native opaque renderers can still traverse or render a whole body; a small viewport does not establish bounded rendering cost.

- **Pointer and navigation routing.** Use Pi’s terminal input decoding and effective bindings. Hit testing checks both horizontal and vertical bounds. Wheel input over conversation gutters or disclosure headers goes directly to the primary conversation. Translate interior body events into the original child’s rows and offer them to that child first; when native content has scrolling, pass unused movement to the conversation at either edge. Standard tool cells without inner scrolling move with the conversation. Keep native scrollbar hover, track clicks, dragging, and redraw, including scrollbar priority at gutter edges. Native Page Up, Page Down, prompt navigation, and Find target the primary chat viewport rather than a painting interval. Preserve overlay priority and composer behavior.

- **Keyboard disclosure access.** Use the existing Pi-registered Alt+G shortcut to transfer focus from the composer to the nearest visible render-group, agent-activity, or activity-item disclosure. Reuse configured selector up/down actions to move between disclosures, confirm to toggle, and cancel to return to the current composer. Collapsed group and item headers use `>`; expanded headers use `▼`. Preserve the established agent activity header appearance. Keep disclosure markers visible without an extra focus arrow. Highlight focused render-group and activity-item disclosures with the native selection treatment; agent activity focus underlines only its summary. Inline thoughts do not enter disclosure navigation. Use native focus dispatch and overlay restoration. No slash command or separate reading view is introduced.

- **Selection and copy.** Own selection geometry within the chat view using occurrence, rendered-row, and terminal-cell endpoints. Traverse expanded content between endpoints, including native preview text and offscreen rows within fully expanded output, while excluding hidden content. Reuse native `app.message.copy`, copy-on-select, and clipboard transport. Constrain selection highlighting to content inside the existing output padding so conversation gutters and the native scrollbar remain unselected. Copy uses native content rows and excludes padding, alignment margins, and scrollbar glyphs without trimming meaningful indentation. Preserve selection during ordinary scrolling; clear it when collapsing, reflow, or selected-content changes invalidate the range, including a scrollbar mode change that changes content width. Clearing selection does not delay agreed automatic disclosure transitions.

- **Search corpus.** Search retained readable source fields on the active branch and its ancestry, including messages, thoughts, commands, tool results, and pre-compaction originals. Extracted activity headings remain searchable in canonical thought source. Match Markdown link labels and code bodies, excluding structural markup and hidden destinations. Keep source-field references, revisions, and match ranges rather than a joined corpus. Sibling branches are excluded. Revalidate results after source changes or branch rebasing.

- **Search input and reveal.** Reuse Pi's search input with an owned source-result controller because native Find searches rendered lines. Selecting a hit opens its ancestor disclosures and fully expands only the selected native output control, creates any missing historical native row at its source-ordered position without changing Pi's session projection, and reveals it through the logical viewports. Resolve split activity bodies through their original source references; a match in one operation opens that row without opening its siblings. If retained source cannot reliably identify one split operation, reveal and highlight its owning source call without fabricating a match or resurrecting the aggregate custom renderer. A hit on hidden thinking temporarily reveals only that occurrence using native thought Markdown. Navigation or a query change moves or removes the reveal; closing Find removes it. Hide thinking remains unchanged. This applies to retained and pre-compaction thoughts too. A hit on an extracted activity heading opens the containing agent activity without reinserting the heading or adding an excerpt. Highlight exact text only where it is rendered. Add no new search mode, placeholder, separate preview, or rewritten tool result.

- **Effective renderers and lifecycle.** Resolve current tool provenance, theme, Markdown environment, and default activity-body renderer choices after relevant lifecycle changes. Preserve the native Markdown transformation chain while selecting built-in native or generic default renderers for activity bodies. Rebind painting and input adapters when Pi replaces its renderer during mode switches. Forward root invalidation to the saved native root once, then invalidate owned geometry and presenters. Dispose adapter subscriptions and operation references with the owning host/session; do not retain an old extension runner after reload or session replacement.

- **Cleanup.** Release owned timers, subscriptions, search and selection state, mark adapter callbacks inactive, and restore only methods and roots still owned by this adapter. Clear the owned scrollbar's native hiding timer only while the chat root is still owned; do not change a scrollbar retained by a later owner. Restore temporary prototype observations promptly. Release borrowed component references without disposing the native components. Wrappers retained by another owner must become inert after disposal; owned historical presenters follow their own lifecycle. Do not overwrite a later owner's host changes during restoration.

## Out of Scope

- Editing Pi's source, maintaining a Pi fork, replacing its client, or creating an external application, service, terminal installer, or viewer. A requirement that needs a broader implementation must return to discussion.
- A separate transcript-reading overlay, a `/transcript` command, or another navigation view.
- Model verbosity, reasoning effort, model selection, and other model controls. This package changes presentation.
- Planning and todo workflows, subagent workflows, pending-question and recorded-answer workflows, and message actions. Their existing native integrations remain usable; this spec does not build their packages.
- Reimplementing the composer, attachments, skill references, Markdown engine, Pi's default activity-body renderers, terminal protocols, image transport, themes, clipboard transport, retries, reconnection, compaction, or agent execution.
- Moving tool adapters, item summaries, or group-summary logic into pi-codex-tools or a new shared package. Its scoped provider-fact changes are covered by the companion core-tool specification; its model-facing contract and execution semantics are not redesigned here.
- Inferring unknown or replacement-tool semantics from names alone, scraping rendered output or orchestration source, general shell parsing, speculative group summaries, tool exclusion lists, provider-specific group exceptions, or requiring every tool author to implement a new grouping protocol.
- Persistent manual disclosure preferences, embedded source markers, content-based occurrence matching, a duplicated transcript buffer, and a speculative hashing dependency.
- Searching sibling branches, hidden Markdown destinations, or discarded content that is no longer retained; search excerpts or a separate result-preview surface.
- Full disclosure interaction in regular mode, rewriting terminal-owned scrollback, unverified claims of compatibility with arbitrary Pi releases, or lifecycle support for abandoned custom SDK extension discovery.
- A new published UI framework, terminal-specific helper packages, speculative configuration, or performance claims unsupported by measurements.

## Further Notes

**Operator catalog:** adapters live in [tool-adapters](../../packages/pi-chat/src/tool-adapters). The [registry](../../packages/pi-chat/src/tool-adapters/index.ts) tries the core-tool adapter, the built-in adapter, and then the generic fallback. [ActivityItems](../../packages/pi-chat/src/activity-items.ts) supplies effective call facts and caches the resulting items. [item-summary](../../packages/pi-chat/src/item-summary.ts) formats each item; [GroupSummaries](../../packages/pi-chat/src/group-summaries.ts) aggregates their operation types. The host owns disclosure and default body rendering, not tool interpretation.

The [built-in adapter](../../packages/pi-chat/src/tool-adapters/built-in.ts) requires Pi's `builtin` provenance and a supported native tool name. The [core-tool adapter](../../packages/pi-chat/src/tool-adapters/core-tools.ts) checks the extension's source path against its owning `pi-codex-tools` package; Pi load-source labels such as `cli` are not tool identities. A retained ownership receipt can identify a historical call when current provenance is absent, but cannot override a known replacement. Nested operations carry their own provenance and receive the same check. Processed results must retain valid factual metadata before the adapter combines them with activity records. Otherwise the [fallback](../../packages/pi-chat/src/tool-adapters/fallback.ts) renders the available call and result generically.

The [command classifier](../../packages/pi-chat/src/tool-adapters/command.ts) is shared by native bash and verified core commands. It recognizes only supported unambiguous reads, searches, and listings; other commands keep their command summary. The [core activity decoder](../../packages/pi-chat/src/tool-adapters/core-activity.ts) validates result metadata and reconciles live and retained records by identity and revision. Neither module parses orchestration source or rendered output to guess an action.

| Tool family                                          | Operation mapping                                                                                                               | Detail rendering and required facts                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pi built-in read, grep, find, and ls                 | Read, search, or listing; registered-skill reads retain their verified classification                                           | Native preview/expanded activity bodies; effective arguments, authoritative results, and public skill metadata where applicable.                              |
| Pi built-in edit and write                           | Edit                                                                                                                            | Native preview/expanded activity bodies; actual target and outcome, with counts only from verified change data.                                               |
| Pi built-in bash                                     | Command or a confidently recognized read, search, or listing                                                                    | Native preview/expanded activity bodies; effective command and actual outcome, using the same conservative classification as extension commands.              |
| Core exec_command and write_stdin                    | Command or a confidently recognized read, search, or listing; meaningful input/collection outcomes retain their own attribution | Generic default preview/expanded activity bodies; effective command/input, stable process and operation identity, actual status, and applicable output.       |
| Core apply_patch                                     | One edit operation for each known affected file                                                                                 | Generic default preview/expanded activity bodies scoped to that file; actual action, target, outcome, available change content, and optional verified counts. |
| Core view_image                                      | Image inspection                                                                                                                | Generic default preview/expanded activity bodies; path/status at the origin and image displayed once in its collecting native result, respecting preferences. |
| Execution cell with its own nonempty output or error | One execution activity item                                                                                                     | Generic default preview/expanded activity bodies; explicit script ownership excludes attributed child content. Empty entries are omitted.                     |
| Other extensions and unknown or replacement tools    | Specific mapping only with reliable adapter facts; otherwise a generic operation with a tool-name item summary                  | Generic default preview/expanded activity bodies from the effective call and processed result. No provider protocol is mandatory.                             |

To change a mapping, edit its named adapter and the corresponding catalog row. A new mapping supplies the existing `CallFacts` → `ActivityItem[]` contract and enters the registry before the fallback. Each item needs a stable identity, operation type, actual status, and its own applicable body; a call need not produce exactly one item. Keep required provider facts and provenance checks in that adapter. Keep shared summary formatting and disclosure code independent of the new tool family.
