## Problem Statement

Pi users need to follow current activity, inspect earlier agent activity, and find retained conversation content without reading an unbroken stream of commands, thoughts, and output. Existing extensions provide parts of this experience, but their overlapping rendering and input changes can conflict.

The chat view groups consecutive activity and collapses earlier agent activity while keeping the final response visible. Pi's native Hide thinking choice controls whether thoughts appear inline. It must operate inside Pi's terminal interface, preserve the original conversation, and reuse native content presentation. It must not require a separate application, service, Pi fork, or modifications to Pi's installed source.

Generic execution titles and operation counts do not identify the agent activity hidden inside a render group. Opening a group can still leave commands indistinguishable, and a single tool call can change several files or run several commands while exposing only one shared disclosure. Pi's default collapsed renderers can also reveal previews and errors before the user chooses to inspect an operation. Users need consistent item summaries and independent activity bodies across built-ins, the core toolset, and other extensions.

An eligible finished activity item should not require opening an otherwise redundant group before reaching its own disclosure. The item and its native output control still serve independent inspection choices. Running activity, uncertain outcomes, and other excluded groups need their existing wrapper.

After agent activity collapses, scrolling into the final response can repeatedly jump back to “Worked for.” Selecting answer text or returning keyboard focus to the composer does not prevent the jump. Dragging the scrollbar can skip the affected position, but ordinary scrolling must work without that workaround.

A current render-group header still describes operation categories even when the native working indicator already identifies the selected operation. Users need that existing operation label in the appropriate group, while older or aggregate-summary groups continue to describe their combined work.

Users also need to copy an exact command, its retained output, an edit's retained diff or result, and an older final response without selecting wrapped terminal rows or exposing hidden work.

Before this revision, an explicit enclosing closure remained effective after cancellation or after the final was corrected to commentary. This could hide interrupted activity or a revoked answer under a disclosure that should no longer be available. Eligibility must govern both automatic and explicit closure while retaining the user's choice if the same activity qualifies again.

## Solution

Build `pi-chat`, one extension that owns the main chat view in Pi's fullscreen mode. A chat view is the primary conversation surface alongside the composer; a transcript is a separate history-reading overlay and is outside this package's scope.

The extension composes Pi's existing message components and activity body components into occurrence-aware agent activities, render-group disclosures, and native thought Markdown in ordinary chat flow. Final responses appear after their agent activity and remain visible when that history closes. Expanded render groups expose every activity item in ordinary conversation flow, and opened bodies use native preview or expanded output sizes according to their own state without a group or body height cap; visible thoughts have no separate header, viewport, or disclosure. Hide thinking removes thought rows completely while retaining their source and native working labels. Source Find temporarily reveals only its selected hidden thought occurrence without changing Hide thinking.

Pi-chat translates native built-ins and the optional neutral activity contract into a common activity-item model. Extension providers describe semantic operations without depending on this package; chat never recognizes their package paths, tool names, or private records. When the complete conditional singleton rule retains the outer wrapper, the collapsed render group shows `>` and either its existing current-operation label, such as `Reading native-host.ts`, or an aggregate group summary such as `Edited files, ran commands`. Expanded headers make the same text choice with their existing marker. An eligible singleton instead exposes its existing item directly: “Worked for” → “Read README.md” → native output control. Omission changes neither the item’s expansion nor its native output state. Opening a retained group exposes individual activity items with their existing disclosure choices. New groups and items inherit Pi’s native global expansion state, which defaults to collapsed. A collapsed activity item contains only `>` and a specific item summary, such as `Ran git diff --check` or `Edited GLOSSARY.md +8 -1`. Opening one row reveals Pi's native output control in its current state, showing the collapsed preview by default. Clicking that control expands or collapses its output independently of the item and its siblings. Closing and reopening an item or ancestor preserves the native output choice. Built-ins use native renderers; extension operations use semantic command, file, or output headings with Pi's generic default result rendering in both states. Pi's preview belongs inside an open item; an extension's custom renderer does not satisfy this default rendering boundary.

One tool call can produce zero or several activity items. Commands and changed files receive independent rows when reliable facts support them. Registered skill reads have `Read <name> skill` labels across native reads and declared command operations. Empty completions, successful polls, and returned script text produce no additional action. Command progress and submitted terminal actions update the origin. Raw script output and input errors remain searchable through Find without creating activity. Explicitly declared error facts retain their existing context or failure item. Original calls and results remain searchable; selecting raw source temporarily reveals its native presenter when needed, including calls with visible operations. Missing or invalid metadata retains generic fallback.

Pi continues to own conversation data, execution, effective Markdown, default activity-body rendering, the composer and surrounding dock, themes, terminal protocols, and final painting. One isolated host adapter supplies the private runtime access required for exact native component identity and composition. Pi 1.1.0 and later are the primary target. Compatibility depends on required capabilities rather than a version string; real-host tests also retain coverage for Pi 1.0.2. Regular mode and the history printed on exit retain native behavior.

Open command items place Copy command beside the native command heading and Copy output below the native result, including failures. Open edit items place Copy diff below an actual retained diff, or Copy output below a textual result without one. One Copy response action follows the complete settled final response outside its agent activity. These actions use Pi's clipboard helper and existing focus navigation; source content and native renderers remain authoritative.

Keep each displayed layout position distinct when preserving the reading position. Scrolling past a collapsed agent activity must advance through the final response and remain there on redraw. Preserve existing selection and keyboard focus, and keep the current reading anchor during actual content growth or resize; continue following the end only when it was already followed.

Offer an enclosing disclosure only for renderable activity with a qualifying final in an uncancelled turn. Otherwise reveal activity in source order and remove its header. While eligible, honor the retained preference before applying the automatic default. Child inspection prevents only default collapse; Find makes an explicit open choice. Preserve descendant states and the memory-only lifetime. Providers without final-phase information continue to select a final only after settlement, without prose inference.

## Implementation Decisions

- **Scoped copy placement.** Eligibility follows the existing semantic activity kind, independently of tool name or failed status. Only commands, edits, and settled recognized final responses gain actions. Copy command sits beside the native command heading; command Copy output and edit Copy diff/Copy output occupy compact result footers below the native output, right aligned where space permits. A narrow layout may put the heading action on its own line without clipping. Final Copy response is left aligned below the entire answer and outside agent activity. Closed items show no actions; open items retain them in both native preview and full-output states. Ancestor collapse hides actions with their item. Preserve native headings, labels, statuses, body rendering, image ownership, and all independent expansion choices.

- **Copy payload ownership.** Read the displayed item's retained source payload at activation. Copy command uses authoritative arguments or operation source, never a shortened summary. Copy output joins all retained text with the existing text-part convention, preserving meaningful indentation and newlines while removing terminal styling. Exclude labels, wrapping, padding, and presentation-only omission notices; include retained failure text. For edits prefer an actual raw retained patch over decorated diff text, retaining its exact structure. An actual retained per-file diff is eligible; counts, speculative previews, current files, and parent arguments do not establish one. Without a diff copy the retained textual result. Respect existing intentional sharing within an operation, but never substitute a parent tool's entire result for every projected operation or file. Do not rerun, reread, or recover discarded data.

- **Final-response copying.** Reuse the existing activity index, final-message/part recognition, and settlement rules. Once settled with a recognized final response, bind one action to that answer's stable source occurrence and selected text parts in source order, joined with Pi's existing message-to-text convention. Copy original Markdown, preserving text-block whitespace, code fences, links, and lists. Exclude thoughts, commentary, tool activity, elapsed summaries, and controls. No prose inference, per-paragraph controls, new detector, or global last-answer handler is permitted.

- **Clipboard and feedback.** Use the public coding-agent copyToClipboard helper and await it. Explicit actions ignore unrelated text selection; native global app.message.copy retains selection preference. Empty or unavailable values are disabled and cannot write or report success. Partially retained output copies only what remains and uses the existing hint/status mechanism to explain the limit. Show Copied briefly only after success, restoring the original label within unchanged row geometry. Report rejection through the existing UI error/status mechanism. Clear timers and invalidate asynchronous callbacks on component disposal, reconstruction, reload, or session replacement. Copy text only.

- **Action interaction and isolation.** Extend the existing focus entry, configured selector navigation, confirmation, cancellation, and visible focus styling to enabled actions; recover focus when an enclosing item disappears. Add no shortcut or setting. A copy click consumes activation before native output toggling, ancestor handlers, or selection. Preserve disclosure choices and reading anchors. Controls are presentation-only: omit them from selected answer/output text and source-search matches without changing original messages, model-visible content, or provider inputs. Reuse native theme and output padding; feedback must not change height.

- **Package and ownership.** Pi-chat owns native presentation, activity indexing, summaries, disclosure, and source search. It independently validates the documented generic activity format; it does not import or recognize companion packages or their private formats. The format adds no separate package or shared runtime module. Unmodified extensions remain supported through generic fallback.

- **Native content boundary.** Pi remains the canonical owner of messages, session entries, model context, execution, and the native event reducer. Borrow native message components and use Pi's default activity-body rendering for activity-item projections. Preserving an extension's custom renderer chain is superseded for those activity bodies. Never insert markers into message content, replace messages for rendering identity, rerun tools, or maintain a second joined conversation buffer. Render-only source references and native rendered-line caches do not become conversation history.

- **Runtime compatibility.** Use one in-process adapter as the accepted exception to the repository's usual public-extension-only boundary. Check required functions when acquiring hooks and preserve native chat-root ownership. Missing hooks must produce an error naming the function; missing hooks or competing ownership prevent activation, restoring changes made during a failed attachment. Do not gate on Pi's version string. Pi 1.1.0 and later remain the primary target. This enclosing delta is verified only against installed Pi 1.1.0, using one coherent native dependency tree without changing repository dependencies; earlier secondary 1.0.2 evidence retains its original scope. Function presence alone does not prove future behavioral compatibility. Prefer public APIs, retaining private fallbacks only where required by the established runtime contract.

- **Host acquisition and root replacement.** Capture the actual `InteractiveMode` through a scoped observation of the native widget method reached by `ctx.ui.setWidget`; restore the prototype descriptor immediately. Verify TUI mode and the same session manager. Save and replace `fullscreenLayoutRoot`, reusing the exact pending-message, status, widget, editor, and footer containers. Leave the native document, chat container, and event reducer alive. Use the original document in regular mode and for history printed on exit.

- **Reload bootstrap.** Native history can be constructed before `session_start` on reload or session replacement. During extension initialization, temporarily observe `renderSessionEntries`. Recognize the owning runner by the function identity of the extension's registered relationship-entry renderer, install the instance adapter before history construction, and restore the prototype. Disarm any remaining observer at `session_start`; use widget acquisition for initial TUI startup. Support the normal Pi CLI lifecycle. Abandoned extension discovery through custom SDK loaders is outside this lifecycle contract.

- **History assembly and binding.** Call native `renderSessionEntries` with a shallow array referencing original entries. Observe its entry-local `flatMap` projection on that array to associate actual projected items with their source entry and item ordinal, leaving entries and messages untouched. Pass the items to the original `renderSessionItems` through a scoped iterator so association remains available during native tool, notice, and message construction. Preserve native selection reset, projection rules, and options; restore the scoped method in `finally` and fail explicitly if association is lost. This retains a dependency on the native `flatMap`-then-`renderSessionItems` path. Observe insertion and removal paths. Associate each original native custom-entry component with its actual source entry whether Pi appends it or inserts it directly before a streaming assistant component. Cover live construction and replay through the same adapter; an append-only observer is insufficient. Source identity alone does not establish agent activity membership. Keep unpersisted native notices by component identity and insertion position. Do not trigger an extra destructive history rebuild.

- **Native component association.** Associate assistant content parts and adjacent thinking runs with the children produced by native construction, including its trimming and thinking aggregation. Rebind those references after native assistant updates recreate children. Preserve native semantic terminal markers. Bind activity items to stable operation identities and their original call, result, entry, and content-part references. Reuse suitable native activity-body components and create default activity-body components for split operations as needed; do not duplicate an extension's active custom renderer. Do not display both projected operations and their original aggregate card. Images retain one visible owner.

- **Operation facts and lifecycle.** Adapters normalize public tool events, effective arguments, processed results, and reliable retained provider facts. The generic activity adapter consumes the documented format through Pi's event bus and retained result/activity details. Stable source-scoped identities distinguish commands, per-file edits, and execution failures. Preserve initial operation order and update existing rows through yields, waits, late completion, and later prompts. A parent return, failure, or agent end does not establish a child's outcome. Routine activity records remain invisible and do not become group boundaries.

- **User-message layout.** In fullscreen chat, render the existing native `UserMessageComponent` at the full chat width, retaining its full-width themed background bar. Align its rendered content as one block to the right with native right padding while preserving relative Markdown indentation and layout. Use the native blank padding row to fill the bar background during cell-aware composition. Keep OSC 133 markers at the row prefix, translate child pointer coordinates, and let search and selection use the displayed aligned rows. Copying selected user text excludes the existing output-padding gutters and added left layout margin while retaining content indentation; do not inset the native component again. Preserve original message data, regular mode, and printed-exit rendering.

- **Conversation gutters.** Reuse the current native `outputPad` on both sides of the whole conversation viewport, including messages, disclosure headers, and activity bodies. Count it once; add no columns, minimum gutter, second inset, or setting. Zero padding means no gutter. Wheel input over this space scrolls the conversation directly before a child can consume it. Recompute horizontal bounds with padding and content-width changes. Keep the native scrollbar region and its pointer priority, including at a gutter edge. Composer, dock, and overlays retain their geometry and priority.

- **Native presentation settings.** Pi remains the source of settings, defaults, and allowed values. Read its current `outputPad` and native transcript scrollbar mode before layout; do not duplicate settings or introduce new flags. Use native components for render-group and agent-activity headers with the current padding, including the agent activity divider. Pi updates its live message and tool presenters; propagate padding changes through available native setters on detached historical presenters. Use native scrollbar style callbacks and `getContentWidth()` before measuring or aligning rows. Native `always` reserves its gutter, `auto` retains native overlay and hiding behavior, and `hidden` leaves it absent. Reuse native track clicks, thumb dragging, hover, timing, and painting. The older Pi 1.0.2 tool presenter has a fixed inset and its settings path can rebuild history; preserve those native behaviors rather than adding private compatibility code.

- **Absent historical content.** Materialize rows omitted by Pi's compaction-aware display projection through native factories into a detached destination, without populating editor history or clearing live pending-tool state. Use historical tool initialization without execution-start behavior or speculative edit previews. For otherwise-hidden thought bodies, use native assistant construction with a render-only array referencing the original thought blocks and the current Markdown environment. Reuse these owned historical presenters until a relevant invalidation or lifecycle change requires replacement.

- **Occurrence identity.** Assign a stable presentation handle to each source occurrence. A live handle points to the current live message and content part; after native persistence, promote that same handle to its committed entry and part reference. Use source entry and projected item ordinal where one entry yields several native items. Content equality, hashes, callback order, timestamps, and screen position do not determine occurrence identity. Equal progress and final text therefore remain independently addressable.

- **Incremental indexing.** Index the raw active branch once, including retained originals omitted by compaction. Reconcile appended entries and changed live occurrences incrementally, and rebase on session or branch changes. Retain references, classifications, revisions, and relationships rather than copied message bodies. Scrolling and collapsing consume the existing index; they do not scan history or hash unchanged content. No hashing dependency is required by this design.

- **Actual input delivery.** Observe the message objects passed to the particular agent's initial prompt operation and returned by its steering and follow-up queue drains. Preserve calls and return values unchanged. Certify delivery only when the corresponding user message starts. An agent listener ordered after native session persistence joins delivered objects to committed entries. Submission intent, queued text, or an input-handler snapshot cannot establish delivery, including when queued prompts contain identical text.

- **Agent activity relationships.** A delivered steering message continues the current agent activity and forms a user boundary between render groups. Every user message remains visible when agent activity is collapsed. Expanding agent activity restores agent activity around the same user occurrences in source order, without duplication. Derive final-response spacing from the last retained visible row, including an intervening notice, rather than an earlier user row. When that last row is a user-message bar, keep one neutral blank line before the final response; reuse native spacing rather than adding a second gap. A delivered follow-up starts a new turn with its own agent activity and answer relationship. An assistant message boundary or agent-loop boundary alone does not begin new agent activity.

- **Standalone extension notices.** A positively identified standalone extension notice without established agent activity membership remains visible while the surrounding known agent activity composes with its selected final response. Keep activity within the turn, retained user rows, and notices in one native-ordered sequence. Closing agent activity hides only its known activity within the turn; reopening it restores those activities around the same retained rows without duplication. Visible notices continue to split render groups. A notice alone does not create an empty agent activity disclosure. Preserve actual request, history, and compaction boundaries, stop at agent activity for a different known turn or an unidentified message row, and never move a notice after the selected final response ahead of it. Do not infer notice ownership from arrival time, the current request, or matching text. This treatment does not make every native status or unknown row transparent to agent activity composition.

- **Relationship persistence.** Append only minimal native custom session entries for certified delivery, agent activity, and final-phase relationships needed on replay. They contain classifications and source references, never copied conversation text or disclosure choices, and remain outside model context. Interpret references within the session journal so copied history in a fork can be rebased. Persist established facts, not guesses that attempt to repair missing provenance.

- **Historical uncertainty.** When historical delivery or phase provenance is unavailable, leave only the uncertain agent activity relationships expanded. Preserve known ordering, tool disclosures, inline thoughts, and search. Do not invent boundaries, phase labels, or explanatory chat messages. Missing historical provenance is distinct from an unsupported host structure, which prevents adapter activation.

- **Activity eligibility and summaries.** Every tool provider participates through the adapter path, including unmodified extensions through the fallback. Consecutive activity items accumulate across assistant messages until visible commentary, visible thoughts, user rows, another standalone non-tool item, or an explicit boundary intervenes. A tool-call or execution-cell boundary alone does not separate groups. Omitted reasoning does not split activity. Group eligibility does not depend on successful classification. The group-summary module derives group summaries from operation types and reliable facts, independent of provider names and renderer content.

- **Group summary lifecycle.** Compose type summaries in a stable order, retaining the established loaded-tool, generic-tool, edit, read, and command ordering and summarizing execution activity items where present. Use sentence-initial case for the first segment, lowercase for later segments, and commas between segments. Identity-based counting and existing distinct-target rules determine singular or plural wording without printing an operation count as a substitute for the description. Unknown activity items use a useful tool-name fallback without invented semantics; their group summary uses the generic operation type. Running operations change the relevant type wording while the aggregate still summarizes all included types. The header may instead show its selected current-operation label under the rule below; this does not change the aggregate summary itself. Observe actual lifecycle facts, including continuing agent activity after a parent returns. A missing result alone does not prove running agent activity. Ordinary scrolling reads cached summaries. Working labels independently consume the same validated facts; summaries do not write their native slot.

- **Current-operation group headers.** Reuse the existing operation selection and formatting governed by the [activity specification](tool-activity.md). Show the selected operation’s label only in its owning group, using existing identities and current-activity context, including established continuation and exploration behavior. Otherwise use the existing aggregate summary with unchanged category wording, ordering, deduplication, and singular/plural rules. Reevaluate the text choice when context changes even if item identities do not. Preserve the full label and apply existing terminal-width truncation only for display. Never copy the rendered native indicator text into groups: it can be truncated, describe another group, or contain a thought title. This adds no selection policy, lifecycle state machine, thought-heading rule, parser, configuration, or provider contract.

- **Render group lifecycle.** Keep logical group identity and choices while conditionally omitting only an eligible singleton’s outer disclosure. Use the complete pinned reference rule below after visible activity boundaries have been projected. Manual expansion or collapse is not an additional eligibility exception. Omission never changes item disclosure or native-output state. A wrapper needed again restores its existing group choice; new groups and items inherit Pi’s current global expansion state, normally collapsed. Preserve choices through growth, completion, failure, cancellation, and individual ancestor toggles until an explicit individual or global action changes them. A retained collapsed group shows only its marker and applicable current-operation label or aggregate group summary; opening it exposes all items in ordinary flow. One call can contribute several activity items.

- **Complete singleton rule.** The parity target is ChatGPT.app, bundle com.openai.codex, version 26.1013.31256, build 20586. Source inspection pins both caller guards and the helper; it does not establish live app interaction. Every condition in this table is required.

| Condition                    | Required for omitting the wrapper                                                         |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| Presentation unit            | It is a group, not an already standalone item.                                            |
| Preservation override        | The caller’s singleton-preservation override is off.                                      |
| Completed-status header      | It is not the latest visible unit carrying a non-null completed-status header.            |
| Header state                 | The group is in summary state.                                                            |
| Cardinality                  | The logical group contains exactly one activity item.                                     |
| Item lifecycle               | The item is inactive under its type-specific lifecycle predicate.                         |
| Patch file count             | The original patch changes exactly one file.                                              |
| Patch visualization activity | The original patch has no visualization activities; the reference treats absence as zero. |

- **Summary state and completion.** Summary state applies unless the group is the latest visible unit, effective header progress is active, and the activity slice is open. The reference uses a supplied header-progress flag, otherwise turn progress. Latest visible means the projected activity sequence, not the terminal viewport. In Pi, use established ownership, visible activity boundaries, qualifying final-response evidence, and settlement. Earlier inactive singletons may unwrap while later activity continues; a finished operation in the latest open group stays wrapped. Closing activity can permit unwrapping during the final stream. In the reference, an execution is in progress only while not interrupted and its parsed command is unfinished. A patch remains in progress while success is absent or null; a false outcome is finished. Dynamic tools, MCP calls, and web searches use their completion flag; automatic approval review uses its in-progress status; other supported types use their corresponding lifecycle predicates. Success is not required.

- **Reference applicability and uncertainty.** Pi’s enclosing agent activity header is independent of the reference’s completed-status header slot. Current supported Pi adapters have no singleton-preservation override, group completed-header slot, or patch visualization activity input. Document those applicability limits without adding settings, visualization support, or invented values. Native and generic tool outcomes use their authoritative completion facts. Shared edit rows retain the original operation’s lifecycle and file cardinality before per-file projection; an unattempted file can belong to a finished failed patch. A non-running label or synthetic result body alone proves no completion. Unknown outcomes, missing original patch facts, or ownership that cannot establish summary state retain the wrapper. Records that combine interruption with uncertainty cannot establish Codex’s interruption exception. Reliable replay follows the same rule; unsupported concepts and lossy historical facts limit exact parity.

- **Wrapper transitions and access.** Reuse surviving item presenters and source references. When a focused header disappears, focus its surviving item when visible, otherwise use the existing composer fallback. Preserve a surviving occurrence and local reading position; map a disappearing header anchor to the surviving item where possible. Apply existing selection invalidation when displayed text changes. Recompute eligibility after Hide thinking, Find reveal, and meaningful boundary changes. Find opens only required ancestors; revealing an already unwrapped item does not overwrite a dormant group choice, while a raw-source reveal that restores a wrapper opens that required ancestor. Pointer geometry, source reveal, native output controls, final-response placement, and the configured global action keep their established behavior. The global action also updates retained logical group choices while wrappers are absent.

- **Disclosure interaction and lifetime.** Follow Pi’s configured `app.tools.expand` action and native global expansion flag; Ctrl+O is only its default, never an extra binding. The action sets eligible enclosing disclosures and all descendant group, item, and native-output states. An enclosing disclosure is available only with a qualifying final, an uncancelled turn, and renderable collapsible activity. When unavailable it has no keyboard or pointer toggle, and a global action neither overwrites its retained preference nor creates one for a future header. New groups and items inherit the native flag. The action also updates logical group choices while singleton wrappers are omitted. Individual ancestor toggles and removal of an ineligible enclosing header preserve descendant choices; the next global action explicitly sets descendants. Retain the same activity's enclosing preference through temporary ineligibility and apply it when eligibility returns. Choices remain in memory through redraw, growth, updates, completion, settings reconstruction, and resize, resetting at existing restart, reload, and session/branch reconstruction boundaries. Do not store choices in content or relationship entries, or change Hide thinking or final-response visibility.

- **Native tool provenance.** Record observed built-in identity and working directory in compact private custom entries bound to the original assistant entry/content index, call identity, and arguments. Restore matching records on the active branch without recreating execution or copying result bodies. Missing or invalid records keep the historical generic fallback; the current registry cannot prove a past call was built in.

- **Adapter organization and selection.** Keep a generic activity-contract adapter, a verified native built-in adapter, and the generic fallback behind the local registry. Valid metadata selects the generic path, including an explicit empty operation set; absent, unsupported, or invalid metadata falls back. Providers interpret their own effective tool identity. No extension name or package-path allowlist belongs in chat, and no third-party tool must adopt the protocol to remain usable.

- **Common activity-item description.** Describe an activity item with stable identity, originating source references, order, operation type, action/target facts, actual lifecycle status, optional verified change statistics, and an activity-body payload or reference with explicit availability. Adapters translate facts into this description; shared chat formatting produces item summaries and aggregates group summaries. Tool-call, execution-cell, and process identities retain ownership and continuation relationships without fixing the number of rows or grouping their disclosures. Splitting a tool call's presentation does not create synthetic model-facing tool calls or session messages.

- **Item disclosure and native output state.** A closed activity item renders only `>` and its specific item summary, with no body, preview, diff, image, omission notice, or error message. Opening it reveals Pi's native output control in its own state, collapsed to a native preview by default. Use native renderers for verified built-ins and semantic command/file/output headings with generic default result rendering for extension operations in both preview and expanded states; do not carry forward custom extension result renderers. Delegate output clicks to Pi so that expanding or collapsing output leaves the item open. Preserve both choices independently through redraw, updates, individual ancestor toggles, and settings reconstruction; retain the existing in-memory/reload lifetime. The configured app.tools.expand action sets item and output states together, and new controls inherit its native flag. Keep the specific command summary while output is a preview; it may shorten when full output is expanded. Beyond the scoped copy actions, do not add another custom control, preview renderer, height limit, setting, or shortcut.

- **Command and edit item summaries.** Share the full pinned Codex command-recognition behavior across built-in and extension adapters, including syntax, option handling, formatting helpers, directory changes, and general-command fallback. Preserve effective paths independently of shortened display names. The [tool-activity specification](tool-activity.md) defines the reference revision and exact coverage. Keep actual scripts and tests labeled `Running`/`Ran`. Do not infer actions from orchestration source or rendered output. Built-in editing tools and the core patch tool map to edit operations. A patch can produce one row for each affected file, with only that file's applicable inputs, result, and outcome in its activity body. Show additions and deletions only from verified change data; omit unavailable counts instead of inferring them from requested replacement text or current disk contents. Do not report unattempted or failed changes as successful edits.

- **Activity configuration.** One package-local module exports operator-adjustable command recognition, item and group wording/order, display-path shortening, operation-body headings, and plain text working-label templates. Defaults follow the pinned reference; operator edits take effect on reload. Configuration changes presentation, not execution, outcome facts, or model guidance. Keep Pi-owned settings at their native source; add no settings UI, persistence layer, or shared package.

- **Pending tool calls.** A live call whose arguments are still arriving contributes no activity or group count before dispatch. Execution, result delivery, or interruption resolves this state. Preserve generic presentation for dispatched tools without valid metadata, real failures, and unknown retained outcomes. Never identify pending orchestration by tool or package name.

- **Results and failures.** Returning or forwarding text adds no activity. Retain all processed script results and errors for source Find, including calls with visible operations. Actual failed operations remain visible once. Input/collection calls and script results add no operation merely because they fail; a valid empty snapshot remains empty for a failed result. Existing providers and history may still declare error facts, which retain their labeled call context or independent failure presentation. Successful children keep their outcomes. Submitted terminal commands update the original operation. Valid zero-item metadata is distinct from absent metadata. Raw orchestration arguments remain retained source.

- **Activity-body retention and replay.** Separate compact operation descriptions from bounded activity-body output. Activity-body output limits must not remove known command or file rows, distort group summaries, or replace known outcomes with uncertainty. Mark missing or omitted activity-body content explicitly and explain it only when the relevant row is opened. Reconcile the latest reliable records on the active branch without recreating live resources. Keep older history usable through available original data and honest fallbacks; do not invent missing operations, counts, outcomes, or payloads. Preserve effective hooks and authoritative processed results when accepting live or retained facts.

- **Final-response selection.** Keep provider phase, selected final, settled outcome, enclosing eligibility, and explicit preference separate. Associate provider phase and item completion with the exact normalized content occurrence, including when several provider items share one assistant message. A supported final qualifies with nonblank text or an exactly associated provider item status of `completed`; an output-item done event, generic turn completion, or error alone is insufficient. An unfinished blank replacement revokes qualification. Keep the selected final outside earlier activity without text matching. Completed blank finals retain an exact source boundary without fabricated prose or blank answer rows, and native trailing notices remain visible. Do not compose across unidentified rows or uncertain historical ownership merely because a selected final exists elsewhere. Existing settled final references can restore a completed blank selection; phase-only history lacking qualification evidence remains visible. Native user and standalone activity ordering remains intact.

- **Agent activity collapse.** Enclosing collapse requires a qualifying final, an uncancelled turn, and renderable collapsible activity. Losing eligibility reveals activity and removes its header even after explicit closure; retain that preference for the same activity's requalification. While eligible, an explicit individual/global choice takes precedence over the automatic default. Explicit child inspection prevents only default collapse; Find records an open preference, and a later eligible manual closure remains effective. Ordinary scrolling, text selection, and header focus do not defer collapse. A valid partial final can remain eligible after a non-cancellation error; failure alone is not a blanket expansion rule. Actual cancellation at settlement, including after agent-end, removes eligibility; an idle abort does not retroactively cancel a successfully settled turn. Descendant choices remain independent unless a global action changes them. This supersedes the earlier policy allowing manual closure independently of eligibility.

- **Reference scope.** Target the pinned ordinary local conversation path in Codex 26.1013.31256, build 20586. Its final-start predicate requires final phase, non-asynchronous delivery, no asynchronous user-input marker, and nonblank text, completion, or structured output. Pi uses its exact text/item-completion facts; separate app-level structured-output and asynchronous user-input forms are absent and are not invented. Ordinary JSON text follows the text path. Reference forced expansion comes from other view/workflow modes; it is neither Pi's global toggle nor the child-inspection hold. Preserve Pi's memory-only inspection lifetime rather than adding cross-turn reference-mode state.

- **Agent activity header.** Display `Worked for <minutes>m <seconds>s` followed by `▶` when collapsed or `▼` when expanded. Derive whole elapsed seconds from the delivered-request entry timestamp to the last committed agent activity entry at settlement; while unsettled, use the current redraw time. Do not count queue waiting or restart the duration on reload, and add no timing metadata or timer. Render the summary with the native muted color and a native thin divider below it, both using the current output padding. Leave a neutral blank line above the header and below the divider in both disclosure states. Focus underlines the summary only; the header and divider have no background.

- **Providers without final-phase evidence.** When the provider supplies no usable final-phase information, treat the text of a qualifying terminal assistant message as one final response only after agent activity settles. Do not split its prose into commentary and answer, infer phase from wording, or promise early collapse without evidence. Preserve cancellation and missing-final behavior.

- **Thinking visibility.** Reuse Pi's native `hideThinkingBlock` setting and its existing controls. When true, omit reasoning rows entirely, including placeholders, headers, spacing, and disclosures; group consecutive activity items across omitted thoughts and recompute conditional singleton presentation. ## Out of Scope

- Other recommendations in the UX comparison: removing native-preview controls, compact read/search rows, new live labels, bounded scrolling, new menus, new settings, visualization support, and unrelated status redesign. This revision changes only eligible singleton outer wrappers and the state, focus, and geometry needed to preserve existing interactions.

- For the enclosing eligibility delta: singleton-group changes, labels, output previews, bounded scrolling, thought presentation, message menus, new settings, persistent preferences, new dependencies, installed Pi edits, other Codex view/workflow modes, and a secondary Pi-version test matrix.

- For the current-operation header revision: new activity-selection or lifecycle rules, thought-heading policy, command parsing, configuration systems, provider contracts, singleton unwrapping, copy actions, native preview changes, scrolling changes, or broader Codex parity.

- Editing Pi's source, maintaining a Pi fork, replacing its client, or creating an external application, service, terminal installer, or viewer. A requirement that needs a broader implementation must return to discussion.
- A separate transcript-reading overlay, a `/transcript` command, or another navigation view.
- Model verbosity, reasoning effort, model selection, and other model controls. This package changes presentation.
- Planning and todo workflows, subagent workflows, pending-question and recorded-answer workflows, and message actions beyond the explicitly scoped command, edit, and final-response copy actions. Their existing native integrations remain usable; this spec does not build their packages.
- Copy controls for reads, searches, directory listings, skill reads, generic tool output/failures, thoughts, commentary, images, user messages, activity groups, or turn headers; Copy file/Copy path; image clipboard support; a general action framework, package, dependency, persistence schema, settings UI, or visualization scaffolding.
- Reimplementing the composer, attachments, skill references, Markdown engine, Pi's default activity-body renderers, terminal protocols, image transport, themes, clipboard transport, retries, reconnection, compaction, or agent execution.
- Moving tool adapters, item summaries, or group-summary logic into pi-codex-tools or a new shared package. Its scoped provider-fact changes are covered by the companion core-tool specification; its model-facing contract and execution semantics are not redesigned here.
- Inferring unknown or replacement-tool semantics from names alone, scraping rendered output or orchestration source, general shell parsing, speculative group summaries, tool exclusion lists, provider-specific group exceptions, or requiring every tool author to implement a new grouping protocol.
- Persistent manual disclosure preferences, embedded source markers, content-based occurrence matching, a duplicated transcript buffer, and a speculative hashing dependency.
- Searching sibling branches, hidden Markdown destinations, or discarded content that is no longer retained; search excerpts or a separate result-preview surface.
- Full disclosure interaction in regular mode, rewriting terminal-owned scrollback, unverified claims of compatibility with arbitrary Pi releases, or lifecycle support for abandoned custom SDK extension discovery.
- A new published UI framework, terminal-specific helper packages, speculative configuration, or performance claims unsupported by measurements.
