# Chat owns activity items and Pi renders their activity bodies

`pi-chat` owns the tool adapters, activity items, and render-group summaries. Adapters live in organized modules inside the package and translate built-in and extension tool facts into one activity-item model. Tool-specific interpretation belongs in those adapters; grouping and disclosure use the common model. Providers supply execution facts without owning chat summaries or grouping. Unmodified extensions use the same path through a generic adapter, with their tool name as the fallback description. Tool identity and provenance must support any more specific interpretation. This supersedes the earlier restriction to built-in descriptions and provider-owned presentation.

Consecutive operations form a render group, preserving the [activity-order boundaries](0013-transcript-activity-order-and-inline-thoughts.md). A tool call can produce several activity items: a patch changing three files produces three edit rows, and an execution cell running several commands produces separate command rows. Execution cells do not impose a shared disclosure. Visible standalone non-tool items and explicit activity boundaries separate groups, while omitted reasoning and execution cell boundaries do not. Execution status collapses with its operation, render group, and agent activity; the final response remains separate.

The collapsed group shows `>` and a group summary summarizing its operation types, such as “Edited files, ran commands.” Opening the group exposes all its activity items in conversation flow, without a group scrolling area. New groups and items inherit [Pi's global expansion state](0014-fullscreen-transcript-interaction.md), which defaults to collapsed. A collapsed activity item shows only `>` and a specific item summary, such as “Edited GLOSSARY.md +8 -1” or “Ran git diff --check.” It shows no result body, output preview, diff excerpt, image, or error message. Edit counts appear only when verified change data supports them; otherwise the item summary omits the counts.

Each open activity item contains Pi's native output control in its own current expansion state, with a collapsed preview by default. Built-ins use their native renderers; extensions use Pi's generic default rendering. Clicking the native control expands its full output or returns to its preview without closing the item. Closing and reopening an item or ancestor preserves that native choice; the configured global expansion action sets both states. Use [native output sizing](0021-bounded-render-group-scrolling.md) in either state, with no custom preview or additional viewport. A command item keeps its specific summary while its output is a preview and may shorten to “Ran command” when the native output is expanded. Pi's preview is inside the open activity body and never replaces the summary-only closed item. An extension's custom renderer does not satisfy this default rendering boundary merely because it uses native controls. Running activity changes the relevant wording without replacing the group summary with one activity item's summary; thought working messages remain separate. This supersedes the earlier rule that opening an item forces its native output expanded.

An execution cell's own output or error appears in one separate execution activity item when it does not belong to a child operation. That entry follows the same disclosure rules, omits empty content, and does not duplicate child output. A failed execution activity item does not change successful child operations to failures, and an error before any child starts remains accessible. The provider associates continuing facts with the initiating execution, preserving the lifecycle ownership in [ADR 0024](0024-core-tools-use-native-extension-lifecycle.md). The package's adapter translates provider facts; routine journals are not standalone visible entries.

Compact operation descriptions survive activity-body output limits so rows and group summaries remain accurate. Opening an entry whose activity body was omitted explains that omission. Retained history without reliable operation facts does not acquire invented rows, change counts, or outcomes.

Command adapters share conservative classification of confidently recognized file reads, searches, and directory listings. Unsupported or ambiguous syntax keeps the command item summary, such as “Ran <command>.” Unknown, replacement, or historical calls without reliable facts must not be assigned invented action semantics. Rendered tool output and orchestration source are not used to infer actions.
