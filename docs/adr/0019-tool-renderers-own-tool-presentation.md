# Chat owns activity items and Pi renders their activity bodies

`pi-chat` owns activity items, summaries, and disclosure. Providers and consumers independently implement the optional, documented activity data format over Pi's existing result details, event bus, and retained custom entries. There is no separate contract package, runtime dependency between the extensions, package-name check, or private producer-record decoder in chat. The shared agreement is the data format; producer construction and consumer validation remain local to their respective packages. Built-ins retain their native adapter; extensions without valid activity metadata retain generic tool presentation.

Consecutive operations form a render group, preserving the [activity-order boundaries](0013-transcript-activity-order-and-inline-thoughts.md). A tool call can produce several activity items: a patch changing three files produces three edit rows, and an execution cell running several commands produces separate command rows. Execution cells do not impose a shared disclosure. Visible standalone non-tool items and explicit activity boundaries separate groups, while omitted reasoning and execution cell boundaries do not. Execution status collapses with its operation, render group, and agent activity; the final response remains separate.

The collapsed group shows `>` and its applicable [current-operation label or aggregate group summary](0020-render-group-lifecycle-and-singleton-preservation.md), such as “Reading native-host.ts” or “Edited files, ran commands.” Opening the group exposes all its activity items in conversation flow, without a group scrolling area. New groups and items inherit [Pi's global expansion state](0014-fullscreen-transcript-interaction.md), which defaults to collapsed. A collapsed activity item shows only `>` and a specific item summary, such as “Edited GLOSSARY.md +8 -1” or “Ran git diff --check.” It shows no result body, output preview, diff excerpt, image, or error message. Edit counts appear only when verified change data supports them; otherwise the item summary omits the counts.

Each open activity item contains Pi's native output control in its own current expansion state, with a collapsed preview by default. Built-ins use their native renderers; extension operations use a semantic command, file, or output heading and Pi's generic default result rendering. Raw orchestration arguments remain in retained source rather than the normal operation heading. Clicking the native control expands its full output or returns to its preview without closing the item. Closing and reopening an item or ancestor preserves that native choice; the configured global expansion action sets both states. Use [native output sizing](0021-bounded-render-group-scrolling.md) in either state, with no custom preview or additional viewport. A command item keeps its specific summary while its output is a preview and may shorten to “Ran command” when the native output is expanded. Pi's preview is inside the open activity body and never replaces the summary-only closed item. An extension's custom renderer does not satisfy this default rendering boundary merely because it uses native controls. When the header uses an aggregate group summary, running activity changes the relevant category wording; item summaries remain separate. The native working label independently selects current work from the same validated facts under [ADR 0022](0022-native-rows-in-an-owned-transcript.md).

Activity lists describe work. Returning text, forwarding a child result as a string, or combining several results never creates an additional Output activity. Command output remains in its command body; raw execution results remain available through retained-source Find, including calls that also have visible operations. Input/collection calls and script results create no operation solely because they fail. Their errors remain in model results and retained source; do not infer a new operation or assign the error to a command by matching strings. A valid empty operation snapshot remains empty even when its tool result reports failure. Missing or invalid metadata still means generic fallback. Show actual failed operations once and keep successful child outcomes successful. For providers or retained records that explicitly declare separate execution-error facts, retain the existing labeled call context or independent failure item. Native images remain inspectable once through their collecting result. This supersedes the earlier automatic failure-item rule for script results as well as the nonempty-output rule.

Continuing command output and terminal submissions update the originating operation's action facts, preserving the lifecycle ownership in [ADR 0024](0024-core-tools-use-native-extension-lifecycle.md). Meaningful actions may have separate rows; a collection receipt alone is not an action. Routine journals remain invisible.

Compact operation descriptions survive activity-body output limits so rows and group summaries remain accurate. Opening an entry whose activity body was omitted explains that omission. Retained history without reliable operation facts does not acquire invented rows, change counts, or outcomes.

The approved copy controls compose native bodies only for semantic command and edit items, including failures. Copy command belongs beside the native command heading; Copy output and Copy diff belong below the native result, right aligned when space permits. Closed items remain summary-only, and open native previews retain the actions. A shell-based read stays a read, and a generic failed tool does not become a command. Each action reads its item's retained authoritative payload, respecting intentional shared operation ownership while keeping projected commands and files distinct from unrelated parent output. Prefer a retained raw patch over decorated diff text; absent an actual diff, copy the retained textual result without reconstructing file history.

Use Pi's public text clipboard helper, preserving transport and errors. Empty values disable copying; partial retention uses the existing hint/status mechanism. Only resolved writes show brief Copied feedback within fixed row geometry. Native theme, padding, focus, disclosure, selection, images, and scrolling remain authoritative. Controls and omission labels are not copied content, and disposed actions cannot update replaced UI. No native renderer fork, new clipboard implementation, package, dependency, setting, or persisted action state is introduced.

Command adapters share the full command-recognition behavior of the pinned Codex build bundled with the reference app, including shell syntax acceptance, formatting helpers, path handling, action ordering, and fallback. A remaining unknown action makes the entire submitted script a general command; separate submitted commands retain independent actions. Reference changes are explicit package changes verified against its complete command cases; a few common read examples do not establish parity. Parsing describes commands without executing them. Registered skill files use a `Read <name> skill` summary whether read by a native tool or a declared command operation. Resolve skill identity from Pi's public skill metadata and the effective file path, independently of its shortened display name. Returned Markdown, orchestration source, and provider identity do not determine actions.

An empty parsed action list retains a general command activity, its outcome, and its body, matching the app's display fallback. This preserves commands such as a failed directory change. An explicitly empty operation snapshot still represents zero operations.

One package-local configuration module contains the operator-adjustable command recognition and activity wording, including item summaries, group summaries, operation-body headings, and working-label text templates. Its defaults follow the reference. Operators can adjust recognized command names and wording without editing parser algorithms or renderers. Configuration affects presentation only; lifecycle facts, source ownership, execution, and model-facing tools remain fixed. Native Pi settings continue to own padding, keybindings, scrolling, and output expansion. This is an activity configuration entry point, not a new package or repository-wide settings framework.

Pending tool calls contribute no operation activity until execution or reliable operation facts begin. Do not label a still-arriving call `Called … (status unknown)`. After dispatch, preserve generic presentation for tools without valid facts, explicit failures, and unknown retained outcomes. This lifecycle distinction applies to every tool and requires no orchestration-tool name check.

Command facts may include the shell executable and argument prefix. The consumer uses these generic facts for command recognition; it never interprets a producer's opaque argument schema. Older facts retain their Bash-compatible interpretation. This optional metadata changes presentation only.

For native calls observed while chat is active, retain the verified built-in origin and working directory in a compact private custom entry, bound to the assistant entry, content index, call identity, and original argument value. Restore that evidence on reload and fork; a changed argument binding, an unobserved historical call, or a replacement without reliable facts keeps generic presentation. No result body or execution resource is stored in this provenance record.
