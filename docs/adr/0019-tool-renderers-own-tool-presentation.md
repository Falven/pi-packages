# Chat owns activity items and Pi renders their activity bodies

`pi-chat` owns activity items, summaries, and disclosure. Providers and consumers independently implement the optional, documented activity data format over Pi's existing result details, event bus, and retained custom entries. There is no separate contract package, runtime dependency between the extensions, package-name check, or private producer-record decoder in chat. The shared agreement is the data format; producer construction and consumer validation remain local to their respective packages. Built-ins retain their native adapter; extensions without valid activity metadata retain generic tool presentation.

Consecutive operations form a render group, preserving the [activity-order boundaries](0013-transcript-activity-order-and-inline-thoughts.md). A tool call can produce several activity items: a patch changing three files produces three edit rows, and an execution cell running several commands produces separate command rows. Execution cells do not impose a shared disclosure. Visible standalone non-tool items and explicit activity boundaries separate groups, while omitted reasoning and execution cell boundaries do not. Execution status collapses with its operation, render group, and agent activity; the final response remains separate.

The collapsed group shows `>` and a group summary summarizing its operation types, such as “Edited files, ran commands.” Opening the group exposes all its activity items in conversation flow, without a group scrolling area. New groups and items inherit [Pi's global expansion state](0014-fullscreen-transcript-interaction.md), which defaults to collapsed. A collapsed activity item shows only `>` and a specific item summary, such as “Edited GLOSSARY.md +8 -1” or “Ran git diff --check.” It shows no result body, output preview, diff excerpt, image, or error message. Edit counts appear only when verified change data supports them; otherwise the item summary omits the counts.

Each open activity item contains Pi's native output control in its own current expansion state, with a collapsed preview by default. Built-ins use their native renderers; extension operations use a semantic command, file, or output heading and Pi's generic default result rendering. Raw orchestration arguments remain in retained source rather than the normal operation heading. Clicking the native control expands its full output or returns to its preview without closing the item. Closing and reopening an item or ancestor preserves that native choice; the configured global expansion action sets both states. Use [native output sizing](0021-bounded-render-group-scrolling.md) in either state, with no custom preview or additional viewport. A command item keeps its specific summary while its output is a preview and may shorten to “Ran command” when the native output is expanded. Pi's preview is inside the open activity body and never replaces the summary-only closed item. An extension's custom renderer does not satisfy this default rendering boundary merely because it uses native controls. Running activity changes the relevant wording without replacing the group summary with one activity item's summary; thought working messages remain separate.

Activity lists describe work. Returning text, forwarding a child result as a string, or combining several results never creates an additional Output activity. Command output remains in its command body; raw execution results remain available through retained-source Find, including calls that also have visible operations. Missing or invalid metadata means generic fallback, never permission to hide a call. Show a failed operation once. If its call also reports an execution error, include that error as separately identified call context in the failed activity's body, without changing factual ownership or inferring a cause from matching text. An execution failure with no failed operation gets its own failure item. Successful child outcomes stay successful. Native images remain inspectable once through their collecting result. This replaces the earlier rule that every nonempty script result deserves an execution activity item.

Continuing command output and terminal submissions update the originating operation's action facts, preserving the lifecycle ownership in [ADR 0024](0024-core-tools-use-native-extension-lifecycle.md). Meaningful actions may have separate rows; a collection receipt alone is not an action. Routine journals remain invisible.

Compact operation descriptions survive activity-body output limits so rows and group summaries remain accurate. Opening an entry whose activity body was omitted explains that omission. Retained history without reliable operation facts does not acquire invented rows, change counts, or outcomes.

Command adapters share conservative classification of confidently recognized file reads, searches, and directory listings. Registered skill files use a Read <name> skill summary whether read by a native tool or a declared command operation. Resolve skill identity from Pi's public skill metadata and the file path, never from the returned Markdown or a package-specific tool name. Recognized literal command sequences can expose several actions while retaining other commands; formatting-only headers need no separate action when they introduce file reads. Conditional, substituted, redirected, or otherwise uncertain shell syntax keeps its full command summary. For native calls observed while chat is active, retain the verified built-in origin and working directory in a compact private custom entry, bound to the assistant entry, content index, call identity, and original argument value. Restore that evidence on reload and fork; a changed argument binding, an unobserved historical call, or a replacement without reliable facts keeps generic presentation. No result body or execution resource is stored in this provenance record. Rendered tool output and orchestration source are not used to infer actions.
