# Conditionally unwrap inactive singleton render groups

Retain each logical render group's identity and choices, but omit its outer disclosure when the complete singleton rule of ChatGPT.app (bundle `com.openai.codex`, version `26.1013.31256`, build `20586`) permits it. A completed read can therefore be inspected through “Worked for” → “Read README.md” → its native output control. This removes a redundant group header while preserving the independent activity-item disclosure and native preview/full-output state accepted in [ADR 0019](0019-tool-renderers-own-tool-presentation.md). This decision replaces unconditional singleton preservation; it does not change [grouping boundaries](0013-transcript-activity-order-and-inline-thoughts.md), final-response placement, or native output flow.

Every reference guard must pass: the projected unit is a group; the singleton-preservation override is off; it is not the latest visible unit carrying a non-null completed-status header; its header state is summary; it contains exactly one activity item; and that item's type-specific lifecycle is inactive. For a patch, its original change set must contain exactly one file and no visualization activities. Count activity items in the logical group, not calls, filenames, output lines, or viewport rows. Preserve original patch provenance before any per-file projection.

Summary state applies unless the group is the latest visible unit, effective header progress is active, and its activity slice remains open. The reference uses the explicit header-progress flag when supplied, otherwise turn progress. “Latest visible” describes the projected activity sequence, independent of viewport position. An earlier inactive singleton can unwrap while later work continues. A finished operation in the latest open group remains wrapped. Established activity closure can permit unwrapping while the final response still streams.

Completion need not be successful. The reference treats an execution as in progress only while it is not interrupted and its parsed command remains unfinished. A patch is in progress while success is null or absent; false is a finished outcome. Dynamic tools, MCP calls, and web searches use their completion flag; automatic approval review uses its in-progress status. Other supported types use their corresponding lifecycle predicates. Pi must use authoritative operation facts rather than equating any non-running label with completion. For a projected patch file, the original operation's outcome and file count control eligibility; a file's unattempted outcome alone proves neither completion nor failure of the patch.

Pi maps header progress and slice closure to established agent-activity ownership, visible activity boundaries, final-response evidence, and settlement. If those facts cannot establish summary state, preserve the wrapper. Its separate enclosing “Worked for” disclosure is not the reference's completed-status header slot. Supported Pi adapters expose no singleton-preservation override, group completed-header slot, or patch visualization activity; these reference guards have no additional Pi input in this revision. Do not add settings or visualization support. Records that combine interruption with an unknown outcome remain wrapped until authoritative completion is available. These are representation limits, not a claim of exact parity for unsupported Codex inputs.

Manual group expansion or collapse is not an eligibility exception. Omission never toggles the item or native output control and never deletes the logical group's remembered choice. If a wrapper becomes necessary again, restore that choice. New groups and items inherit [Pi's global expansion state](0014-fullscreen-transcript-interaction.md), normally collapsed; the configured global action updates all available disclosures and retained logical group choices. Growth, completion, failure, cancellation, settings reconstruction, and individual ancestor toggles preserve existing descendant choices. Their in-memory lifetime and reset on restart or extension reload remain unchanged.

When a focused group header disappears, transfer focus to its surviving item when visible; otherwise use the existing composer fallback. Preserve a surviving source occurrence and local reading position, mapping a disappearing header anchor to its surviving item where possible. Follow existing selection-invalidating rules when displayed text changes. Retained wrappers keep their existing summary, chevrons, focus treatment, and unbounded [conversation flow](0021-bounded-render-group-scrolling.md). Find, pointer routing, source ownership, copying, and final-response placement keep their existing contracts.

Logical singleton cardinality is independent of [render-group body eligibility](0019-tool-renderers-own-tool-presentation.md): suppressing a running item never turns a multi-item group into a singleton. Expanded groups expose their body-eligible items in conversation flow without a shared scrolling area. Render-group and activity-item headers place `>` when collapsed and `▼` when expanded immediately after their labels, at the normal terminal font size and line height. Reserve the chevron's width before truncating the label. A retained header without an eligible body has no chevron or disclosure target and reserves no chevron width. The active working header retains its loading indicator on the left. Focused headers use Pi's native selection background, with expansion chevrons still visible and no extra arrow. Individual rows follow the [summary-only collapsed state and independently expandable native output controls](0019-tool-renderers-own-tool-presentation.md).

A retained current header owns the single working row, including its operation label, thought-heading fallback, or `Thinking` fallback. Use the existing active-header and activity-boundary facts, independently of label selection; the native working indicator must exist and the header must actually be displayed. A completed command can leave its group open with a thought heading as the label. Earlier retained groups use their existing summaries, and absent current headers leave the working row below the conversation. This changes neither singleton eligibility nor activity lifetime, grouping, focus, or group/item/native-output choices. The [working-row revision](../specs/pi-chat.md) is specified in [Chat 18](../../.scratch/pi-chat/issues/18-active-accordion-working-row.md); its runtime verification remains separate from the completed singleton revision.
