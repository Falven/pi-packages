# One editor owns draft transactions

The active editor owns draft mutations; with `pi-composer`, native editing actions, text replacement, and attachment membership changes operate on the same Markdown state, selection, and undo history. Paste policy chooses the outcome and attachment handling owns stored contents, while the editor applies the resulting draft change. This keeps both ordinary editing and changes such as replacing selected text with an attachment coherent and undoable between the editor and attachment handling.

The composer's draft identity and targeted replacements are package-owned capabilities behind Pi's public replacement-editor contract. They do not extend Pi's editor interface or add identity metadata to native submission callbacks. Asynchronous work must follow the actual requesting draft and history; matching text alone cannot establish that identity.

Use Pi's public editor APIs first. Extending `CustomEditor` and installing it with `setEditorComponent()` replaces the active editor; it does not adapt another editor or preserve its state automatically. Preserve the selected editor, keep `pi-composer` optional, and pass unhandled input through that editor's existing handling. Released Pi provides text access, insertion, callbacks, and some history operations, but no draft identity or equivalent public asynchronous range-edit contract. Whole-draft replacement cannot be treated as preserving the requesting draft, caret, native paste state, and undo.

A package-local adapter uses private editor capabilities only for identified public API limitations. Scope it to the affected editor instance and clean it up on reload. This community fallback requires compatibility verification using unmodified Pi; prior community integrations alone do not establish that it meets these requirements. Verify native-editor and composer behavior separately, including pending capture, caret and selection, undo, prompt history, identical drafts, session changes, reload, and normal, steering, and follow-up submission ordering. Immediate capture and snapshot reuse remain unchanged.

Delay submission before Pi clears the editor. One Send waits for the captures already running for its draft and required image preparation, updates the original request's references to retained snapshots, then submits that request through Pi's native path. Later edits, undo and prompt history, recovery, and the original normal, steering, or follow-up intent remain intact. Plain text keeps immediate native submission when no attachment work or earlier same-route request needs a wait. A second Send or replaying Enter against a newer draft is not an accepted substitute. Within each route, later text must not overtake an earlier image because of attachment preparation. Verify both editors with other input handlers, preparation failures, and changes in the active run while waiting. Capture still begins when the attachment enters the draft.

Preserving the requested native action does not freeze Pi's run state. If Pi becomes idle before a delayed follow-up reaches native submission, its normal command dispatch applies, including executing `/reload`. The package must not defer settlement to force literal message delivery.

The pre-clear integration passed separate native-editor and composer checks on unmodified Pi. [Ticket 04](../../.scratch/pi-attachments-settings/issues/04-preserve-asynchronous-editor-changes.md) records the public gaps, private dependencies, failed post-clear approach, and passing integration; [ticket 07](../../.scratch/pi-attachments-settings/issues/07-verify-portability-and-restore-pi.md) records runtime versions and pending physical acceptance. These are package capabilities, not additions to Pi's public editor contract. No Pi source changes, global prototype patches, private queue modifications, or silent editor replacement are permitted. Private dependencies remain vulnerable to Pi updates; a compatibility failure requires a specific report and agreement on any necessary behavior change.
