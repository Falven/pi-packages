# One editor owns draft transactions

The active editor owns draft mutations; with `pi-composer`, native editing actions, text replacement, and attachment membership changes operate on the same Markdown state, selection, and undo history. Paste policy chooses the outcome and attachment handling owns stored contents, while the editor applies the resulting draft change. This keeps both ordinary editing and changes such as replacing selected text with an attachment coherent and undoable between the editor and attachment handling.

The composer's draft identity and targeted replacements are package-owned capabilities behind Pi's public replacement-editor contract. They do not extend Pi's editor interface or add identity metadata to native submission callbacks. Asynchronous work must follow the actual requesting draft and history; matching text alone cannot establish that identity.

Use Pi's public editor APIs first. Extending `CustomEditor` and installing it with `setEditorComponent()` replaces the active editor; it does not adapt another editor or preserve its state automatically. Preserve the selected editor, keep `pi-composer` optional, and pass unhandled input through that editor's existing handling. Released Pi provides text access, insertion, callbacks, and some history operations, but no draft identity or equivalent public asynchronous range-edit contract. Whole-draft replacement cannot be treated as preserving the requesting draft, caret, native paste state, and undo.

A package-local adapter may use private editor capabilities only after identifying the exact public API limitation for each one. Scope it to the affected editor instance and clean it up on reload. This community fallback is conditional on a compatibility experiment using unmodified Pi; prior community integrations do not establish that it meets these requirements. Verify native-editor and composer behavior separately, including pending capture, caret and selection, undo, prompt history, identical drafts, session changes, reload, and normal, steering, and follow-up submission ordering. Immediate capture and snapshot reuse remain unchanged.

No Pi source changes, global prototype patches, private queue modifications, or silent editor replacement are permitted. If the experiment fails, report the specific failure and settle any necessary behavior change before proceeding. Private dependencies remain vulnerable to Pi updates; the transaction guarantees are requirements, not verified host capabilities.
