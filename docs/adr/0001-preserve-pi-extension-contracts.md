# Preserve Pi extension contracts

Every package targets unmodified, released Pi and uses its documented public services and effective overrides first, preserving native dispatch, provider composition, and the single active replacement editor. Pi owns terminal input decoding, keyboard protocol negotiation, native keybinding configuration, hardware-cursor visibility, and hyperlink capability detection; Pi or the terminal activates links through the system's default handler, and the terminal owns cursor appearance. Where public support is missing, inspect community implementations and record the chosen package boundary and its limits before adopting a fallback.

## Consequences

Package installation and verification must not depend on changes to Pi's source, replacement compiled host packages, or a vendored Pi fork. Interfaces added only to a local Pi build are not official extension contracts. Effective image visibility, resizing, width, and editor padding already have public settings support and remain independently implementable.

Pi Attachments resolves only its two namespaced action entries, Attach… and Manage attachments…, from `keybindings.json` in Pi's active agent directory. It registers the selected concrete keys, descriptions, and handlers through the public `pi.registerShortcut()` API. Package-owned action resolution follows community practice; Pi handles the registered shortcuts. Sharing Pi's file does not make that resolution Pi-owned. Configuration follows file editing and `/reload`; `/hotkeys` is Pi's existing read-only display. Do not add a keybinding configuration menu, another shortcut file, a separate keybinding manager, or a shared configuration framework. Preserve defaults, explicit remapping and unbinding, native conflict handling, and command access. The widget uses a stable `/attachments` command hint; `/hotkeys` shows the effective shortcuts. Released Pi has no public query for accepted extension shortcut winners after conflicts, so the package must not present configured keys as verified winners.

Attachment thumbnail size lives in Settings inside Manage attachments…, including for an empty draft. Reuse Pi's public `SettingsList`, `getSettingsListTheme()`, and `ctx.ui.custom()` for appearance and keyboard behavior. An attachment-owned user settings file persists only this package preference across restarts and reloads manual edits on `/reload`; native preferences remain supplied by `pi.getSettings()`. This persistence follows community practice, while the UI components are official services. Released Pi has no `registerSetting()` API or integration for adding preferences to central `/settings`. Keep Small, Medium, and Large bounds of 12 columns by two rows, 24 columns by four rows, and 48 columns by eight rows. Medium remains the default; aspect ratio, Pi's image visibility, general image width, and available terminal space remain constraints. Settings adds no primary action or configurable shortcut. Evidence and runtime acceptance belong in the [attachment specification](../specs/pi-attachments.md).

Deferred image preparation must follow the effective delivery-time image policy and reject only the affected submission, preserving unrelated active and queued work, retained history, and recovery. It remains a separate milestone until Pi provides a public delivery boundary that supports this isolation; aborting the active run or silently dropping a failed image does not satisfy that contract.

The portable submission baseline prepares images before queue acceptance, preserves public input composition, existing images, and recovery, and leaves final image blocking to Pi. Interactive submission uses the scoped editor integration in [ADR 0002](0002-one-editor-owns-draft-transactions.md): one Send waits for already-running capture and required image preparation while preserving the original request and its native submission action. Later text on the same route must not overtake an earlier image because of attachment preparation. Pi retains command dispatch when its active run changes during that wait. Preparation uses the effective policy at that point. Skipping preparation solely because images are currently blocked can lose content when policy later changes; preparing before queue acceptance can still fail for an image that Pi ultimately blocks. These limits remain explicit while delivery-time preparation is deferred. Whole-conversation context transforms do not provide isolated rejection of a queued submission.

The isolated runtime adapter in [ADR 0022](0022-native-rows-in-an-owned-transcript.md) remains a scoped exception for `pi-chat` to acquire native rows and own chat composition, selection, and search. It checks required capabilities rather than Pi's version string and does not authorize private integration in other packages. [ADR 0002](0002-one-editor-owns-draft-transactions.md) separately permits a package-local, editor-instance adapter for attachments only where a specific public API gap is established and a compatibility experiment passes. The attachment exception preserves Pi's source files and native ownership and permits neither global prototype patches nor private message-queue integration.

[ADR 0028](0028-independent-quote-extension.md) separately permits instance-scoped selection and rendering hooks for the independently installed `pi-quote` extension. Pi keeps selection and editor ownership; the package supplies the Quote action and draft insertion without modifying installed Pi or requiring another extension.

[ADR 0031](0031-skill-references-own-compact-presentation.md) separately permits a narrow, reversible, instance-scoped rendering adapter owned by `pi-skill-references` where public Markdown hooks cannot suppress native skill rows. It preserves recorded messages and provider input, requires no chat extension, and permits only generic optional coordination with the active transcript for source Find. This exception does not authorize Pi file changes, persistent global hooks, private message-delivery changes, or claims of compatibility without real-host verification.

[ADR 0032](0032-independent-composer-followups.md) permits `pi-predict` to observe active-composer replacements and decorate its render output where Pi lacks a watermark API. The package also observes the public Agent request function to retain the effective parent context, forwarding requests unchanged. Hooks remain reversible and instance-scoped, with no Pi file changes, replacement composer, sibling dependency, or installation-order requirement.
