# Core toolset

**Status:** implementation in progress; yielded execution blocked by public host API

## Problem Statement

Pi's built-in tools give the agent a different interface for commands, file changes, and images from the fixed tool contract the user wants to use. Tool names alone do not account for the difference. Declarations, instructions, argument encoding, execution, continuation, errors, output limits, and the results sent back to the model all affect how the agent works.

The user needs a package that provides the selected contract while retaining the configured Pi experience. Replacing tools must preserve effective host settings, native interception, explicit tool selection, retained history, and independently installed extensions. A renamed wrapper around the existing tools would neither reproduce the intended behavior nor automatically preserve every integration.

The user also needs verifiable comparisons. Similar answers or a successful demonstration do not establish that the model received equivalent tools or that tool execution behaved the same way.

## Solution

Create the self-contained Pi extension package `pi-codex-tools`. It supplies the core toolset through two direct model tools, `functions.exec` and `functions.wait`. JavaScript executed by `functions.exec` can call four selected tools: `exec_command`, `write_stdin`, `apply_patch`, and `view_image`.

Commands cover local execution, text reading, searching, and listing. Patches cover file creation and modification, including moves and deletion. The image tool and image output helper cover local image inspection. The package replaces equivalent stock built-in capabilities without taking over unrelated extension tools or the rest of the agent interface.

The captured contract is the baseline for the included tool names, declarations, instructions, arguments, results, and behavior. Pi's effective settings, public dispatch, result processing, and normal extension lifecycle remain authoritative. Those accepted differences are explicit, rather than hidden behind a claim of complete application equivalence.

Verification uses the existing real Pi host with controlled provider responses. It observes the outgoing model request, executes the requested tools against real temporary resources, and examines the next outgoing request. Matched live-model trials then measure behavior under equivalent task conditions.

## Implementation Decisions

1. **Scope and target.** Deliver one package for the measured macOS arm64 environment and the configured Responses-compatible provider path. Use normal package discovery, public extension registration, public provider composition, and public lifecycle events. Do not modify Pi, install private runtime adapters, or add platform, provider, or version guard frameworks. Preserve the existing boundary that private integration is an exception for the chat package alone.

2. **Frozen baseline.** Use captured baseline `local-tools-reference-20261013`, identified by canonical source SHA-256 `c96638241baa0167c3603823374d67a616a4d4df5142496a1d13971ece498843`. The canonical encoding is sorted-key, compact UTF-8 JSON. This checksum identifies the complete source capture, not an implemented or validated scoped contract. Extract only the included tool declarations and behavior cases; give that scoped fixture its own identity when created. Updates are deliberate package changes, with no runtime synchronization, alternative profiles, or installed-application dependency.

3. **Two direct tools.** The outgoing selected tool surface exposes `functions.exec` and `functions.wait` with the captured namespace, input form, descriptions, schemas, required fields, optionality, and constraints. `exec` accepts raw JavaScript with the optional first-line execution pragma; it must not become a model-facing JSON code wrapper. `wait` accepts its captured object schema. Preserve the included instructions without broad paraphrasing. Remove only the approved out-of-scope tools, helper overloads, metadata, and related explanatory text.

4. **Four nested tools.** The execution environment exposes `exec_command`, `write_stdin`, `apply_patch`, and `view_image` through its `tools` object. Text reading, searching, and listing use commands. There are no additional read, write, edit, search, list, or alternate-shell aliases. Register the selected operations with Pi so nested calls retain native dispatch. Use public exposure and loadout controls to separate model declarations from callable operations; never confuse a hidden declaration with a permission restriction.

5. **Selection and ownership.** Replace the equivalent stock `bash`, `read`, `edit`, `write`, `grep`, `find`, and `ls` surface only within the user's enabled scope. Explicit Pi selection and exclusions remain authoritative. Do not reactivate excluded registrations to satisfy a hardcoded list. Preserve unrelated tools, their order and model-dependent availability, and extension-owned overrides identified through public provenance. Retained historical calls are not renamed or rewritten. Newly loaded tools apply on the next request after normal loading or reload, including in an existing conversation.

6. **Execution runtime.** Each `exec` evaluates an async JavaScript module in a fresh V8 isolate with the selected host helpers. It exposes no direct Node, filesystem, network, or console APIs. The selected command and file tools remain the route to host operations; this runtime isolation is not advertised as an operating-system sandbox. Preserve the captured restriction against running an outer `exec` invocation in parallel with other tool invocations; independent nested calls may run concurrently when Pi permits them. Yielding completes that outer invocation while its cell continues. Script completion ends its isolate and discards unawaited JavaScript promises. Do not infer cleanup of already dispatched host processes from that promise behavior; process ownership follows the agreed session lifecycle and measured termination behavior.

7. **Retained helpers.** Keep `text`, `image`, `exit`, `store`, `load`, `notify`, `setTimeout`, `clearTimeout`, and `yield_control`. Keep `ALL_TOOLS` as name/description metadata restricted to the selected tools actually available in the session. `text` appends output and stringifies non-string values when possible. `notify` makes another output available immediately using the same value treatment. `exit` successfully ends the script. `store` and `load` share serializable values by string key across executions in the active extension session; a missing key returns `undefined`. Pending timers alone do not keep an execution alive. `yield_control` delivers accumulated output while execution continues.

8. **Image helper scope.** Retain data-URL input and the ordinary object form carrying `image_url` and optional `detail`, including the captured ordinary detail variants and explicit-detail override. Exclude public protocol image-content objects, their metadata, audio emission, generated-image emission, and the shared types or forwarding examples needed only by those excluded helpers. Network image URLs are not introduced.

9. **Declared defaults and limits.** Preserve the following captured declarations. A documented effective range does not by itself establish whether an implementation clamps, rejects, or rounds an input. Check that behavior before encoding it.

   | Operation      | Captured defaults and shape                                                                                                                                                                                                                                                                                           |
   | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `exec`         | Pragma `yield_time_ms` defaults to 30,000; `max_output_tokens` defaults to 10,000. No numeric bounds are documented in the captured declaration.                                                                                                                                                                      |
   | `wait`         | Required string `cell_id`; `yield_time_ms` defaults to 10,000 and `max_tokens` to 10,000. Omitted or false `terminate` waits; true terminates.    | `write_stdin`  | Required numeric `session_id`. Omitted `chars` means an empty-input poll. Output budget defaults to 10,000. Nonempty writes default to a 250 ms wait capped at 30,000 ms.    | `view_image`   | Required local filesystem `path`; `detail` is `high` or `original`, defaulting to `high`. Returns `image_url` as a base64 data URL and the returned `detail`. 10. **Command results.** Preserve the command APIs' required `output` and `wall_time_seconds` fields and optional `chunk_id`, `exit_code`, `original_token_count`, and `session_id` fields. A completion during the call has an exit code; a continuing process has a process session identifier. Preserve field absence instead of fabricating values. Nonzero exits are ordinary command results where the baseline uses that form. Keep partial output and the distinction between launch errors, command exits, tool failures, and script exceptions.

11. **Two kinds of continuation.** Execution cells use string identifiers consumed by `wait`; running commands use numeric session identifiers consumed by `write_stdin`. Do not conflate their state or identifiers. Waiting returns only output since the previous yield and closes a completed cell. Command polling likewise preserves the captured incremental-output behavior. Output limits apply at the appropriate tool and orchestration boundaries, including the meaning of a pre-truncation token count. Do not substitute native line or byte limits for captured token budgets.

12. **Shell preferences and context.** Resolve defaults from the owning execution context, not the extension process's startup directory. Use an explicitly supplied command shell when present, the effective Pi shell preference as its configured default, and the captured default-shell behavior otherwise. Apply Pi's effective command prefix once per launched command. Preserve inherited environment, Pi's managed executable search path, and fresh session metadata. Clear stale inherited session metadata as native execution does. Read effective settings through Pi's public service so trusted project settings and in-memory overrides remain in effect.

13. **Process ownership.** Support pipes and PTYs, retained process handles, input delivery, output polling, completion, and cancellation. A yield deadline is not a process timeout. Reuse suitable public or installed facilities, but do not force the native completion-only shell operation interface to act as a PTY or process-session API. Bound buffers, preserve valid decoding and trailing output, and keep any necessary output spill files private. Cleanup must include owned subprocesses according to the host lifecycle and the observed execution contract.

14. **Native dispatch and results.** Run nested operations through `ctx.executeTool()`, not a tool factory's raw `execute()` method. Preserve validation, blocking hooks, argument mutation, result mutation, image normalization, and native execution events. Return the outcome after these steps. Never reconstruct a discarded result from cached raw backend output, including structured content removed by a result hook. Follow Pi's actual registration precedence and callable-tool rules.

15. **Permissions and integrations.** Pi supplies operating-system permissions and any configured extension or external restrictions; project trust controls resource loading. This package adds no separate approval or sandbox system. Retain the captured permission-related command argument shapes, whose default selection is `use_default`, while honoring Pi's actual authority. Do not invent an approval, elevated access, or isolation guarantee that Pi does not provide. A request requiring an unavailable authority must fail clearly. Hooks keyed to old tool names and injected remote or sandbox operation objects are not automatically transferable. The currently inspected packages do not require such translation; a general translator or remote-backend abstraction is outside this release.

16. **Patches and file integrity.** Implement the selected patch behavior for creating, updating, moving, and deleting files. Verify syntax, matching, validation order, partial-failure behavior, returned changes, and errors against the frozen baseline. Preserve unrelated content and applicable encoding, BOM, and newline behavior. Reuse public `withFileMutationQueue` for local mutations so operations coordinate with native edits and writes, including existing symlink aliases. Do not add another lock service or promise cross-process locking, atomic multi-file transactions, rollback, or cancellation undo. Native fuzzy replacement, argument repair, and path convenience rewriting are not part of the replacement contract merely because native tools provide them.

17. **Images and settings.** Check effective `images.blockImages` before `view_image` reads or returns image bytes or a data URL. A blocked outcome contains no image bytes, including when emitted through `text`. Otherwise, emit images through Pi's normal result pipeline. Preserve `images.autoResize` and the effective routed model's limits, without duplicating normalization against possibly different selected-model metadata. Pi may resize or convert an image despite an original-detail request; this is an accepted host-processing difference. Terminal image visibility remains independent. This rule governs the image operation and normal image emission, not generic scanning of arbitrary shell or text output for encoded data.

18. **Lifecycle.** Live commands, execution cells, timers, and temporary stored values belong to the active extension session. They can survive ordinary prompts in that session. Normal shutdown, reload, quitting, and session replacement through new, resume, or fork operations stop owned live work and clear temporary state. File changes and retained history remain. There is no daemon, process-global survival registry, or restoration of live handles from retained history. Failed or stale handles produce clear results rather than binding to unrelated new work.

19. **Yielded execution feasibility.** Public nested dispatch is designed around an executing parent call; an execution cell can outlive the initial `exec` result. Establish through the public host seam that subsequent nested calls retain appropriate context, cancellation, result processing, events, and attribution when output is collected through `wait`. Do not silently drop activity or use a private lifetime adapter if the public contracts prove insufficient. Report a demonstrated blocker with evidence before expanding scope.

20. **Native composition.** Preserve the configured composer, attachments, skill references, chat presentation, web tools, and prompt/lifecycle extensions. Pi continues to own provider composition, conversation data, retained history, native tool events, and terminal behavior. Tool renderers retain ownership of expanded tool presentation. Generic action labels for newly registered tools are acceptable; this package does not add a chat-specific protocol or infer file operations by parsing arbitrary shell strings. User-entered shell commands remain on their native path.

21. **Internal boundaries.** Keep contract registration and loadout handling, execution-cell state, command-process state, patch execution, and local image conversion as the necessary responsibilities. Prefer existing public helpers and mature installed dependencies. Add only the boundaries needed to implement and verify those responsibilities; do not introduce a general adapter framework, alternate provider stack, configuration surface, or separate history store.

22. **Artifact naming and documentation.** The exact package identifier `pi-codex-tools` is the sole approved source-application naming exception. Names identifying the source application, its vendor, or related products must not appear elsewhere in implementation artifacts, instructions, fixtures, comments, diagnostics, or documentation. Keep only the required glossary, justified architecture decisions, this specification, and individual tickets as documentation. Existing resolved terminology and architecture decisions already cover the core toolset, public extension contracts, and lifecycle; no additional glossary or architecture document is needed for routine implementation details.

## Testing Decisions

1. **Approved primary seam.** Reuse the existing real Pi host fixture with a controlled provider transport. Observe a complete request, scripted model tool call, real tool effect, and subsequent model request. Keep real provider parsing, tool registration, validation, dispatch, hooks, and conversion. Extend this fixture only as necessary; do not create a parallel simulated agent framework.
2. **Prior art.** Existing native-host checks already exercise explicitly selected extensions, tool selection, recorded outgoing requests, staged streaming responses, real filesystem effects, and Responses-style messages. Existing chat and companion-package integration checks demonstrate the same host approach. Native tool tests provide cases for cancellation, image settings, write coordination, and file integrity; they are behavior references rather than internal implementation contracts to copy.
3. **Contract checks.** Assert selected names and namespaces, exact scoped instructions, raw-input grammar, schemas, required and optional fields, defaults, provider encoding, output content types, and the absence of excluded declarations. Preserve meaningful order and distinguish an omitted value from a fabricated one. Do not stop at checking an extension's in-memory registry.
4. **Real effects.** Execute commands and patches against temporary directories; verify created, changed, moved, and deleted contents. Use controlled interactive processes for PTY/input behavior and recognizable output chunks for polling, limits, cancellation, and output draining. Check that failures have the expected effects and subsequent model-visible results.
5. **Host-policy checks.** Exercise effective shell settings, command prefix, current context, session environment, explicit inclusion/exclusion, hook blocking, argument changes, result redaction, image blocking, normalization, routed-model limits, write coordination, and native events. Verify both direct completion and work continuing after a yield. A hook fixture recognizes the new tool names; it must not be presented as proof that arbitrary policies for old names migrate automatically.
6. **Lifecycle and composition checks.** Exercise ordinary prompt continuation, cancellation, reload, shutdown, new/resumed/forked sessions, stale identifiers, and retained history. Run mixed command/patch/image flows with the configured companion extensions and preserved unrelated tools. Observe the native host's actual lifecycle instead of assuming every UI navigation performs the same reset.
7. **Declared versus observed behavior.** Establish the undocumented poll default, numeric boundary treatment, patch behavior, and continuation/image error cases through the fixed baseline before asserting fidelity. Keep an explicit distinction between declaration matches, verified behavioral matches, and accepted host differences. A missing observation is neither a passing test nor permission to guess.
8. **Matched model trials.** Use identical user prompts, starting conversation conditions, repository snapshots, model identity, and supported generation settings. Control temperature, reasoning effort, limits, and seeds only where the provider/model exposes them; record unavailable or uncontrollable parameters rather than pretending equivalence. Keep task-relevant instructions and host settings aligned where possible, and account for remaining harness differences explicitly. Pair or repeat trials where useful to distinguish variance from a repeatable difference.
9. **Comparison outcomes.** Measure task success, tool-selection and argument mistakes, unnecessary calls, elapsed time, and token consumption. Preserve exact request/result evidence for deterministic checks while normalizing only truly incidental identifiers or measurements. Do not require identical free-form assistant text, infer undocumented training history, or claim general superiority from a small trial.
10. **Verification scope.** Each ticket delivers its own complete behavior checks through the same primary seam. The final ticket combines contract conformance and matched trials; it does not defer all testing until integration. Use the repository's existing test runner and focused checks. Add lower-level checks only when a specific external behavior cannot be established at the host seam. Protect credentials and unrelated conversation data when reducing captures to fixtures.

## Out of Scope

- Collaboration, subagents, goals, scheduling, asynchronous user-question tools, clocks, web or browser tools, external tool discovery, desktop automation, worktree management, and application UI integration.
- Additional direct read, edit, write, search, list, or alternate-shell aliases.
- Audio, generated-image helpers, public protocol image-content overloads, and their unused metadata or shared types.
- Replacing Pi's full instructions, workspace guidance, skills, provider stack, model settings, repository-context assembly, compaction, or conversation management.
- A separate approval engine, generic permission-policy translation, automatic inheritance of injected remote/sandbox operations, or a compatibility framework for integrations not used by the current setup.
- Modifying Pi source, using private runtime integration, requiring the source application or its binaries at runtime, or maintaining live work outside Pi's normal extension lifecycle.
- Automatic baseline updates, multiple contract profiles, platform/provider/version guard frameworks, broad portability work, or speculative configuration.
- A new presentation system, custom action-label inference, duplicated history, transaction/rollback services, or stronger filesystem guarantees than the agreed behavior supplies.
- Identical entire requests across different applications, identical generated prose, claims about undocumented training data, or unmeasured performance improvements.
- Extra comparison reports, general design documents, or other documentation beyond the four requested workflows.

## Further Notes

- Implementation has established a public-API blocker for yielded execution. The real-host probe on the installed dependency confirmed stale nested-call records, reused call identifiers, missing late updates, and a stale default cancellation signal after the parent returns. Ticket 03 records the evidence; independent completed-call, process, patch, and image slices can proceed. No private adapter or change to Pi is authorized.
- Re-reading the frozen image declaration corrected the earlier absolute-path assumption: it requires a local filesystem path. A supplemental runtime probe accepted a relative path. The implementation follows that local-path contract and the owning context's working directory.

- The design, verification seam, local tracker, and seven-ticket breakdown are approved. This specification and its tickets are ready for implementation; they do not report an implemented package or completed runtime parity checks.
- The captured baseline dates from 2026-10-13. The source checksum above is independently verified. The selected sample contains completed execution outputs and command results, including nonzero exits. It does not itself establish yielded-cell behavior, retained process sessions, patch execution, local image handling, or boundary truncation. Those are explicit verification work in the corresponding slices.
- The native audit inspected Pi 1.1.0 source and the configured executable, and checked relevant public declarations in the workspace's installed 1.0.2 dependency. Effective settings access and the file mutation queue exist there. This evidence does not prove every required behavior on both versions or authorize a broad compatibility project.
- The approved slices are: a short command through the full loop; interactive process continuation; yielded execution cells; patches; local images; mixed native workflows; and complete contract checks with matched model trials. Their dependencies are recorded in the individual tickets.
- Exact fidelity is scoped to the selected contract and approved exclusions. Pi settings, hook outcomes, image normalization, explicit tool selection, and normal session lifetime are accepted host constraints. Any further material difference must be surfaced rather than folded into an unqualified parity claim.
