# 03: Yield and resume execution cells

**What to build:** Let JavaScript execution yield output while it continues, then use `functions.wait` to collect new output, completion, or termination. Keep explicit stored values available across executions in the same extension session.

**Specification:** [Core toolset](../spec.md).

**Blocked by:** 01 — Execute a command through the complete model loop; 02 — Shared asynchronous output storage for commands and cells.

**Status:** claimed — implementing the approved session-owned continuation contract

- [x] Probe public dispatch after the parent returns and during a later prompt with configured companions. Verify hook blocking, argument changes, result redaction, explicit cancellation, dynamic callable selection, custom-entry rendering/model exclusion, and notification timing. Record native identity/history limitations as accepted differences.
- [ ] Expose the captured `functions.wait` declaration, schema, defaults, and string cell identifier in the actual provider request. Preserve the distinction from numeric command-process identifiers.
- [ ] Implement the execution pragma's yield behavior, explicit `yield_control`, incremental waiting, final completion, and explicit termination against the fixed baseline.
- [ ] Keep one fresh worker per execution and retain it across yields. Release it promptly when the script settles; retain only unread output, terminal results, and necessary pending-operation cleanup metadata. Never create a worker during a wait.
- [ ] Deliver only newly accumulated output using serialized collection and a sequence cutoff. Preserve text/image order and limits; retain a running cell ID and retire a collected terminal result once. Use events and one active-wait deadline timer, with no periodic polling.
- [ ] Complete the selected helper behavior: text, notifications, successful early exit, timers, and serializable store/load. A missing stored key returns `undefined`; timers alone do not keep an execution alive.
- [ ] Keep fresh JavaScript globals for each execution, with no direct Node, filesystem, network, or console APIs. Do not misrepresent this as operating-system isolation.
- [ ] Restrict callable tools and their metadata listing to the selected operations actually available under Pi's active policy. Preserve public dispatch even when scripts coordinate independent calls.
- [ ] Verify notifications through public messages with no unsolicited turn, documenting delivery at Pi's safe boundary instead of promising an immediate extra tool-output event. Verify output and late nested calls after a yield, including redaction that is never reconstructed from backend content.
- [ ] Verify failed scripts, invalid/stale cells, repeated waiting, and termination while work is pending. Distinguish declared behavior from cases still requiring baseline measurement.
- [ ] Commit only each cell's changed stored keys on normal completion, early exit, and ordinary exceptions; discard them on termination. Verify copy isolation and overlapping snapshots without overwriting unrelated committed keys.
- [ ] Keep cell and caller cancellation separate: cancel initial execution before yield, preserve the cell on later wait cancellation, and abort pending operations on explicit termination. Preserve independent returned process handles. Stop intake before cleanup and report cleanup that does not finish within its bound.
- [ ] Preserve live cells and stored values across ordinary prompts, and clear them with the agreed native session lifecycle while keeping file effects and retained history.
- [ ] Record compact, bounded incremental activity through public custom entries with package child identities. Flush full batches and lifecycle boundaries; render interrupted retained records without recreating resources or adding them to model context.
- [ ] Bound worker messages before posting, pending calls, workers, retained cells, unread output, serialized values, and activity metadata. Reuse shared asynchronous storage, fail clearly on overflow, and record concrete limits.
- [ ] Compare completed-call latency to `6bac1a2` and measure wait, output-heavy, concurrent-cell, memory, event-loop, and cleanup behavior separately from model latency. Explain any short-call regression.
- [ ] Demonstrate the complete behavior through the existing host seam using short commands and controlled asynchronous scripts, without requiring the interactive-process slice.

**Implementation evidence:** A controlled real-host probe on the installed 1.0.2 dependency reproduced the lifetime problem. Returning the parent result snapshots and removes its nested-call scope. An in-flight child stays recorded as `unfinished` after it completes; a later call through the saved context reuses the parent's `/1` identifier and adds no record to retained history. Original result-update callbacks deliver no events after the parent returns. On a later prompt, native cancellation aborts the current signal but leaves the saved context's default signal active. Hooks still modify arguments and results, including dropping removed structured content.

Dispatch through an active waiting tool receives that waiting tool's attribution, but cannot account for work between waits. The public call options expose only a signal and an update callback, with no durable scope or reparenting operation. The inspected 1.1.0 source has the same scope-consumption behavior. The original probe passed its seven checks. The approved revision accepts these native limits, owns cell identifiers and activity records through public entries, and passes an explicit cell signal; it does not claim to repair native attribution.

Supplemental observations of the target behavior are retained for [yielding and waiting](../../../packages/pi-codex-tools/test/fixtures/observed/commands/script-yield-wait-and-store.json), [helper lifecycle](../../../packages/pi-codex-tools/test/fixtures/observed/commands/script-helper-lifecycle.json), and [stored-value serialization](../../../packages/pi-codex-tools/test/fixtures/observed/commands/store-serialization.json). Their runtime build identity is unverified. New probes distinguish ordinary text, which does not wake a pending wait, from explicit yielding, which does. Notification delivery is separate and does not wake that wait. Concurrent-wait arbitration and caller-only wait cancellation cannot be independently reached through the available reference controls; serialization and cancelled-wait preservation are accepted package rules, not verified matches.

The current reference allowed dispatched commands to survive both normal script completion and explicit cell termination; their discarded JavaScript callbacks did not run. The approved package contract instead aborts operations still pending at explicit termination and session cleanup. A command that has already returned its own process handle remains independent. Record this difference without changing the user's selected cancellation behavior.
