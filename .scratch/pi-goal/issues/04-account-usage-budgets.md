# 04: Account for usage and budgets

**What to build:** Show trustworthy tokens and elapsed pursuit time, preserve those values through lifecycle changes, and stop future goal work when its soft token allowance is exhausted. Follow the approved [specification](../../../docs/specs/pi-goal.md).

**Blocked by:** 03: Continue safely and honor Stop.

**Status:** partial — implementation, reported-usage captures, compaction, and supported provider-limit precedence verified; the public capability limits below remain open.

- [x] Charge uncached input plus output using the provider's reported usage. Verify Pi's input-plus-cache-write-plus-output mapping against original provider counters; exclude cache reads and avoid counting reasoning again when included in output.
- [x] Establish accounting when the goal becomes active. Creating a goal partway through a turn excludes previously reported work; replacement establishes a fresh baseline excluding descendant usage already reported. A later descendant report can contribute to the current active goal even when that child started earlier; do not add an originating-goal filter to the shared report counter.
- [x] Count each final call's own reported usage once, including nested execution-end events and grandchildren. Verify attribution, reporting cutoffs, concurrency, and duplicate suppression. Pi later aggregates descendant usage onto the root result message; do not charge that aggregate again or claim coverage of subprocesses and tools that omit usage.
- [x] Persist nonnegative exact integer deltas and commit the accounting baseline only after a successful write. Serialize checkpoints so concurrent tool completions cannot charge the same provider usage twice; storage failure cannot silently consume a baseline.
- [x] Record provider usage as pending accounting without flushing solely because usage arrived. Persist at the specified tool-finish, turn-stop, and external-mutation boundaries. A read returns the stored snapshot and can be followed by its own tool-finish accounting. `update_goal` performs its own checkpoint and is excluded from the generic tool-finish checkpoint.
- [x] At pause, clear, or completion, retain only eligible usage known at the relevant boundary. Do not invent missing provider reports or silently charge later reports after active accounting is cleared. Preserve the completion snapshot across interactive cleanup.
- [x] Keep stored status separate from live accounting. Model status updates clear current-turn accounting even when the effective status remains budget-limited. An external mutation with no new token or whole-second progress does not clear an exhausted in-flight ledger; a nonzero checkpoint does. Verify both paths directly.
- [x] Maintain monotonic live pursuit time with fractional carry across checkpoints. Include active waits, exclude paused or unloaded periods, and avoid charging process downtime. Display integer seconds and keep wall-clock timestamps in their specified units.
- [x] Preserve the live clock after raw interruption while the goal remains active. An idle read does not flush it; a later external pause can record the intervening idle time. This is separate from the explicit pause attempted by native Stop.
- [x] Clamp remaining tokens at zero and preserve the soft-limit behavior. Already admitted work can overshoot; exhaustion prevents new continuations and instructs the model to stop substantive work while eligible in-flight accounting continues until its boundary.
- [ ] Preserve budget-limited status across pause or block requests and reject activation with an already exhausted budget. Completion and confirmed provider usage limits retain their specified precedence. A genuinely configured host maximum follows the observed policy without adding an invented default setting.
- [x] Inject the budget notice only at a qualifying tool-finish checkpoint and at most once for the applicable generation. Other exhaustion checkpoints do not guarantee a message, and the message does not itself cancel the turn. Preserve objective data, elapsed time, token values, wrap-up guidance, and the distinction between prose and serialized status spelling.
- [x] Show current persisted usage and effective stop reason in native goal controls and all relevant model results. Emit completion reporting guidance only under the specified conditions, without adding final-response tokens that were unavailable to the completed snapshot.
- [x] Protect replacement goals and other sessions from stale goal-bound mutations and checkpoint writes by both ownership and generation. Distinguish a stale checkpoint from a newly arriving descendant report into the shared counter. Repeated events, resume, objective edits, and session restoration must not create refunds or fresh allowances.
- [x] Verify cache variants, reasoning, large integers, pre-creation baselines, nested usage, concurrency, soft overshoot, failed persistence, time carry, pause/resume, and late reports through the agreed seam. Use narrower controlled checks only for precision, clock, or failure cases that the real-session boundary cannot express clearly.
- [x] Capture original usage, normalized usage, checkpoints, budget messages, and final results in Phoenix. Correlate nested and background work, retrieve captures to verify completeness, and record any attribution or timing gap before claiming delegated parity.
- [x] Preserve public extension boundaries and neutral terminology, complete relevant checks, and leave all unreported-usage and unsupported-provider limitations explicit.

## Implementation verification

The accounting module separates reported usage, the active monotonic clock, and the current outer-turn binding. Its `currentGoal` binding can change on activation or replacement within a run; `activeGoal` retains live clock ownership after a raw interruption. Native retries can emit multiple `agent_start` events before one `agent_settled`; they preserve the same accounting baseline. Provider usage comes from the final persisted assistant entry after message hooks, or the corresponding `turn_end` message, and remains pending until an eligible checkpoint.

All 27 new checks pass on primary Pi 1.1 source `6fb2e7815167e6b19006fc526d1a5d0f5f998787` and the secondary workspace runtime. Eighteen exercise real native sessions; nine use the approved narrow precision, clock, and persistence boundary. The combined accounting, goal, lifecycle, protocol, and continuation suite passes 101 checks on the primary runtime, and its 13 persisted Stop cases also pass. Type checking, scoped lint, formatting, and whitespace checks pass.

The native cases verify pre-creation usage exclusion; 12 charged tokens versus a 22-token root aggregate; completion at the known grandchild cutoff of 7; concurrent reports and a late earlier child after replacement; cache-write and reasoning normalization; post-hook provider usage; repeated retry starts; exhausted model and external mutation cutoffs; final-response exhaustion without a tool notice; completion snapshot retention; raw interruption and idle time; and executed versus rejected tool results. Integer checks cover exact totals above the safe-number range and both token and elapsed-time signed 64-bit overflow without advancing the baseline.

Real SQLite write failures retain pending usage for a later successful checkpoint. Failed settlement suppresses automatic continuation, and failed shutdown still invalidates the extension lifetime, cancels admission, disposes Stop, and closes storage. An unsafe reported number fails visibly and suspends automatic continuation for that session and generation within the loaded extension; later valid checkpoints cannot erase that missing usage. The package cannot recover precision already lost by a provider or tool.

The nine native accounting captures below passed, and all 100 captured input/output fields were independently retrieved and verified. Exact child-abort qualification and cutoffs inside opaque programmatic model calls remain the public capability limits described below. Tools and subprocesses without usage reports remain outside the accounting claim. No configured host maximum is exposed by the inspected extension API, and this change invents no maximum or setting. ## Accounting boundary evidence

On the pinned reference local streaming route, a goal at 92 tokens remains at 92 while its manual summary is held, reaches 184 when that summary reports another 92 chargeable tokens, and remains at 184 after explicit pause and interruption of the held follow-up. Successful compaction also admits the next eligible continuation. The integrated package charges the public `session_compact.compactionEntry.usage` report once. Ticket 05 reproduces the 92-to-184 transition and automatic continuation without an edit or resume. Ticket 07 verifies both provider protocols through RPC: two summary requests contribute a combined 184 tokens, advancing the existing 92-token goal to 276 before its next automatic request.

Trace `673549f09f6e41be85595cea9c6a0b09` has five spans and ten complete fields, independently retrieved and matched against saved payloads, hashes, and byte counts. Evidence is under `/tmp/pi-goal-compaction-zdw10nzm/20261014-025221-e1895706/active_manual_compaction`. Four requests were observed; two completed and two closed without a response. The final snapshots and ten relevant source blobs were independently verified against the pinned source tree. The engine exited zero; checked shared settings and earlier scripts remained unchanged.

Request metadata identifies manual local streaming compaction in its standalone-turn mode. Automatic local compaction shares the inspected charging path but has not been exercised in that reference capture. A separate remote compaction path records a different budget and does not invoke the same goal usage callback; it remains source-only evidence. Pi's successful compaction entry can combine multiple summary requests. That public aggregate cannot prove earlier creation/pause cutoffs inside the summary or recover unreported usage from an aborted summary. Preserve this limit rather than treating the aggregate as per-request observation.

Read-only inspection of the pinned runtime confirms that descendant reports increment a shared counter without an originating-goal filter. Activation snapshots the current total; a checkpoint separately carries the expected goal generation into its database write. Replacement therefore excludes previously reported usage but can include a later report from an older child. Discarding every report from a child started under an earlier goal would change this behavior.

Pi 1.1 exposes each final call's own usage in `tool_execution_end`, with `parentToolCallId` for nested calls. Nested usage is added to a recorder before that public event, and the recorder's aggregate is attached to the root `toolResult` at `message_start` afterward. Observe own-usage end events once and ignore the later aggregate for charging. A required test reports 10 tokens before creation, then 7 from a grandchild, 3 from its parent, and 2 from the root: the goal receives 12, although the eventual root aggregate contains 22. Completion immediately after the grandchild must return the known 7.

Two capability limits remain. Native programmatic model calls expose their private accumulated usage only on the final outer result, so public events cannot reconstruct a creation or completion cutoff inside those calls. Also, `durationMs` proves that execution ran, including zero-duration execution, but thrown aborts and ordinary handler failures share the same public error shape. A nested call can use a separate abort signal. Exact exclusion of all aborted tool-finish checkpoints and associated budget notices is therefore not established by the root signal, error text, or `isError`. Unsuccessful completed results and ordinary executed failures remain eligible; do not suppress every native error. These limits require explicit acceptance evidence and must not be concealed by an approximation.
