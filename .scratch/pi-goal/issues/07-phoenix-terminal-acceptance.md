## Native EOF limitation

Closing RPC input during an unfinished response reproduces `turn_end could not resolve the persisted assistant entry ID`. Native CLI controls with no goal package reproduce the same loss: active EOF exits zero with no persisted assistant; explicit abort followed by settlement and EOF exits zero with one persisted aborted assistant and no boundary error. Both controls make exactly one request. The passive observer exposes the error; the unfinished assistant is absent from native session storage.

The original three-request switch/reload reproduction preserves its two earlier assistants and an active goal at 92 tokens and one second, but loses the unfinished third assistant. A fresh command-created goal can preserve its SQLite row without a session JSONL because the host waits for a user or assistant message before its first file flush. No extra request follows shutdown. These observations do not establish a clean active-EOF persistence boundary or universal reopenability.

Evidence is under `/var/folders/z8/66twpw0n05z3dy2dtkn_z8v40000gn/T/pi-goal-eof-diagnosis.pzelcoqf/diagnosis-index.json`. Independent verification checks 55 artifact hashes across seven cases and seven native source files against the pinned runtime. The two controls under `cli-IJuZSW` use the actual CLI entry point; four controls under `modes-JSRo1E` use the public RPC mode. The remaining case is the original failed reproduction. These diagnostic controls are not Phoenix acceptance captures and are excluded from the 20 accepted process phases.

Source evidence explains the boundary: RPC EOF disposes the runtime; runtime disposal emits shutdown, then aborts and disconnects without awaiting response settlement. The ordinary session-replacement path awaits abort first. No host source change, private integration, synthetic history entry, or inferred user pause was added.
