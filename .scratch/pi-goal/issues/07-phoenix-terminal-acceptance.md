# 07: Complete Phoenix and terminal acceptance

**What to build:** Demonstrate the complete goal workflow through real Pi sessions and the actual terminal, with a reviewable Phoenix comparison of the agent interface and explicit accounting for every material difference. Follow the approved [specification](../../../docs/specs/pi-goal.md).

**Blocked by:** 05: Preserve goals across session changes; 06: Stop unproductive runs.

**Status:** in progress — earlier evidence assembled; final preservation, guard, and terminal acceptance is pending.

- [ ] Assemble the evidence collected by the earlier slices into the full create, inspect, continue, edit, pause, resume, clear, complete, block, budget-exhaustion, usage-exhaustion, and lifecycle scenario matrix. Complete missing cases; do not defer all capture work to this final slice.
- [ ] Collect actual reference-client and Pi evidence for ordinary controls and the work cycle. Label actual-client observations, bundled-runtime checks, deterministic provider scripts, and payload replays separately. Use controlled failures for unsafe or impractical live-provider conditions; keep unperformed cases pending with their consequence for the compatibility claim.
- [ ] Match scenario prompts, initial repository and goal state, model, supported reasoning and sampling settings, limits, and provider route wherever possible. Record real defaults separately from aligned runs, preserve omitted settings, and identify differences that cannot be controlled.
- [ ] Identify each capture boundary: effective host context, final provider request and parsed response events, and transport or gateway request/response data. A pre-conversion context or parsed body must not be described as the final wire or a raw byte capture.
- [ ] Use public context, provider-request, and response-event hooks for Pi. In controlled runs, observe after other transformations and verify against the receiving endpoint. Correlate retries, cache warming, nested tools, concurrent providers, sessions, runs, requests, and tool calls without assuming one request-hook event means one transport attempt.
- [ ] Compare message roles, order, provenance, channels where present, objective delimiters, internal visibility, context placement and repetition, and goal policy descriptions. Record Pi-owned schemas, validation, advertising, and result delivery as intentional native interface choices.
- [ ] Compare preserved goal values, omitted versus null fields, exact integer conversion, call/result correspondence, native programmatic results, and subsequent history. Pi owns error classes and formatting. Do not normalize away lost values or differences in goal authority, ordering, accounting, or state.
- [ ] Compare original provider usage, cache treatment, normalized usage, delegated attribution, checkpoint timing, budget notices, elapsed time, and final snapshots. Treat unreported usage as an evidence limit. Preserve opaque continuation data without claiming to decode it or requiring identical stochastic answers.
- [ ] Retrieve ingested Phoenix records and verify request and response completeness with canonical-payload or byte hashes appropriate to the capture layer. Detect truncation, missing events, absent usage, and unsupported hooks. Keep credentials out of saved evidence and retain the user's persistent provider and tracing settings.
- [ ] Complete actual-terminal acceptance with native Pi and the companion composer, attachments, skill references, and chat extensions in supported load orders. Exercise configured Stop, autocomplete Escape, overlays, retries, compaction, goal controls, session switching, reload, exit, and late-callback cleanup. Recording-terminal assertions alone do not close physical interaction checks.
- [ ] Confirm that Pi source and installed files remain unchanged, no private adapter has been introduced without a separate decision, and effective tools, editor ownership, themes, keybindings, and host lifetimes remain intact.
- [ ] Run the relevant formatting, lint, type, and behavior checks for the implemented feature and affected integration surfaces. Repeat or broaden checks only for changes, failures, or unresolved concerns, and fix substantiated compatibility defects within scope.
- [ ] Record neutral trace references, supported runtime capabilities, verified results, and material limitations in the specification and these tickets. Create no separate comparison report, contract, research note, or extra plan; do not publish the package as part of acceptance.
- [ ] Mark each ticket complete only when its acceptance is demonstrated. No exact-compatibility claim is permitted while a required observable or capability remains unexplained, unsupported, or unverified.
