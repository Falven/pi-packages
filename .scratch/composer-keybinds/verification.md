The first combined attempt mixed file-loaded companion extensions with a supplied composer factory. Pi loads those files before supplied factories, so the later replacement composer discarded their editor decoration and attachment insertion could not confirm its draft. This was a harness-order failure before setup or paging ran. The corrected fixture loads `pi-composer`, `pi-paste`, `pi-attachments`, and `pi-skill-references` as factories in the same order as the existing file-based mixed fixture. The mixed suite also covers exchanging paste and attachment order. A replacement composer loaded after decorators remains outside that supported ordering; no runtime change or broader ordering guarantee was introduced.

The setup proof supports Ghostty 1.3.1 on local macOS with exactly one owned, regular Application Support configuration, no XDG configuration files or includes, no extra Ghostty launch arguments, and a matching verified same-user ancestor process. Discovery can cross the root-owned macOS `login` intermediary. Installation and repeat require native U.S. keyboard input-source and layout identities (`com.apple.keylayout.US`), no modifier remapping, and no higher-priority physical triggers for the three letter gestures. This excludes physical sequence starters as well as direct bindings; default physical digit bindings are unrelated in the verified layout. Removal remains possible after layout, remap, or physical-binding changes.

Within that context, native candidate validation, freshly loaded baseline inspection, and the established loading order and duplicate-trigger last-wins semantics prove the eight appended bindings. Native permission inspection refuses ACL-bearing original or candidate files; ordinary owner, group, and mode are preserved. Contents, metadata, process context, and installation layout are rechecked before replacement. The optional Darwin `KERN_PROCARGS2` probe is an unstable prerequisite and fails closed when unavailable or mismatched. The [specification](../../docs/specs/pi-composer.md#verification-boundary) defines the verification contract; [ticket 02](issues/02-set-up-and-remove-ghostty-keybindings.md#verification) records this implemented subset.

Four native checks passed after review. The existing configuration was inspected read-only: both U.S. keyboard identities and process checks passed, the native validator accepted the configuration, no includes/remaps/physical-letter conflicts/ACLs were found, and default physical digit bindings remained. Three public-command probes used temporary configurations and the real Ghostty/permission tools, substituting only process ancestry/context: a `super+KeyA` conflict was refused, a real `everyone deny write` ACL survived refusal, and an ordinary configuration completed installation, repeat, and removal. These results do not establish the GUI's loaded state or physical input delivery.
