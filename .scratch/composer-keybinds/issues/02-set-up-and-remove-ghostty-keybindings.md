# 02: pi-composer: set up and remove Ghostty keybindings

**What to build:** A user can review and install the specified eight persistent Ghostty forwarding rules with /setup-keybinds ghostty, then reverse that change with /setup-keybinds ghostty remove. The command changes only one marked block in an existing configuration after verification and native confirmation.

**Blocked by:** None (can start immediately).

**Status:** complete

**Specification:** Composer specification, “Ghostty keybinding setup,” “Verification boundary,” and “Setup and page-selection acceptance,” stories 52–64; ADR 0010, “Make terminal keybinding setup explicit and reversible.”

## Verification

The supported pre-write proof is limited to Ghostty 1.3.1 on local macOS with exactly one owned, regular Application Support `config` or `config.ghostty`, no XDG config file, no includes, and no extra Ghostty launch arguments. The command walks Pi's parent chain, including macOS's root-owned `login` intermediary, and requires the selected Ghostty process to have Pi's UID. An optional system Python3 standard-library probe matches Ghostty's executable, account HOME, XDG and startup context. Darwin `KERN_PROCARGS2` is marked unstable by the SDK; denied access, missing Python, an unexpected process-data format or any context mismatch prevents a write.

Installation and repeat verification require the native selected keyboard input source and underlying layout to both identify `com.apple.keylayout.US`. Carbon TIS queries provide those identities through the existing Python probe. Native binding inspection must show no physical `super+key_a`, `super+key_z`, or `super+shift+key_z` trigger, including sequence starters, and native configuration inspection must show no modifier remapping. Default physical digit bindings are unrelated under the verified U.S. layout. Unknown layouts or higher-priority physical bindings prevent installation and repeat success. Removal remains available after these conditions change.

Within that established single-source and keyboard context, native validation checks the exact staged candidate and duplicate-trigger last-wins semantics establish all eight appended bindings. This is a bounded loading-order proof, not a prospective binding inspector or observation of the live GUI. Native `/bin/ls -lde` inspection refuses ACL-bearing originals or staged files. Ordinary owner, group, and mode are preserved, and source metadata and contents are rechecked before replacement. Independent temporary native fixtures demonstrated both Application Support filenames, include resolution, physical-key precedence, ACL refusal, and the install/repeat/remove lifecycle against Ghostty 1.3.1. No live settings were changed.

The product probe was run read-only against the existing same-user Ghostty process: executable identity, UID, stable identity, argc=1, HOME/XDG equality, CFFIXED_USER_HOME absence, account-home equality, and both U.S. keyboard identities passed. The current configuration has no includes, modifier remaps, physical-letter conflicts, or ACL permissions; its default physical digit bindings remain present. Expected roots came from the calling shell. A public-host regression uses the observed node → zsh → root-owned login → same-user Ghostty ancestry shape. Actual interactive Pi ancestry after the fix and physical forwarding remain ticket 03's acceptance checks.

The fixture restores process overrides after failed initialization and closes the host before removing its directory.
