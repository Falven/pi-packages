# 01: Honor effective Pi settings through public input handling

**What to build:** Attachment images, previews, and text entry follow effective Pi preferences on an unmodified installation. Image preparation failures stop the requesting input before queue acceptance and leave its contents recoverable.

**Blocked by:** None (can start immediately).

**Status:** in-progress — the image module is verified independently; full editor and preview acceptance and the required same-route Send-order experiment remain pending.

**Specification:** [Pi Attachments](../../../docs/specs/pi-attachments.md), including its applicable architecture decisions.

- [ ] Read native preferences through pi.getSettings(), preserving Pi's defaults and global, project, and runtime overrides. Do not reconstruct native settings from files or retain dependencies on locally added host interfaces.
- [ ] Honor images.autoResize during image preparation, retain required format conversion, preserve captured originals, and append attachment images without discarding images supplied by other handlers.
- [ ] Honor terminal.showImages and terminal.imageWidthCells in previews, preserve aspect ratio, and apply editorPaddingX to Create from text… through public editor services. Visibility, width, and padding changes never initiate capture. Medium remains 24 columns by four rows; preference selection belongs to ticket 03.
- [ ] Replace delivery-hook image preparation with supported preparation before native queue acceptance and preserve public input composition. Coordinate with ticket 04's experiment so interactive Send waits for required image preparation before Pi clears the editor. Preserve the original normal, steering, or follow-up intent and prevent later same-route text overtaking an image because of attachment preparation. Do not replace Pi's queue, modify it privately, or substitute custom messages.
- [ ] On preparation failure, notify the user, retain requesting-draft recovery, and return the input event's handled result. Throwing alone does not prevent submission. Do not silently omit a failed image, overwrite later edits, or stop unrelated active or queued work.
- [ ] Prepare images even when images.blockImages is currently enabled, since a queued request may become allowed. Preserve Pi's final blocking enforcement. Record that resize settings are applied before queueing and that preparation can still fail for a request whose images would ultimately be blocked; ticket 06 remains deferred.
- [ ] Remove required type dependencies on locally added native submission fields while preserving existing recovery metadata, retained files, and pending recovery across reload and session changes, including --no-session. Editor association and pending Markdown capture use the integration established by tickets 04 and 05.
- [ ] Adapt the existing focused image and text-entry checks to unmodified public host interfaces. Exercise effective overrides, conversion with resizing disabled, retained bytes, supplied images, all three submission routes, and recoverable failures. Confirm native-editor and composer results separately during ticket 07.

**Integration:** Tickets 01–05 remove coupled host contracts in one integration checkout. Focused checks accompany each slice; complete unmodified-Pi startup and regression acceptance belong to ticket 07. Do not invent host shims to make intermediate checks pass.

**Current implementation and verification (2026-10-14):** Image preparation runs in the public input event after retaining the requesting draft and supplied images. Preparation failures notify and return `handled` before queue acceptance. Current image blocking does not skip preparation, and resize settings apply before queueing. Recovery still accepts historical submission metadata without requiring a native submission field.

`registerImages(...)` now returns `{ prepare(request, ctx) }`. The request accepts `text`, optional `images`, and optional `streamingBehavior` from the public input contract. The method freezes the requesting session ID, session file, working directory, text, and supplied-image copies before its first await, saves recovery, then returns `{ text, images }` or `undefined` when no image transformation is needed. Preparation failures reject to the caller with the recovery path; the public input handler keeps its notice and `handled` behavior. Concurrent and later preparation reuse results keyed by retained path, effective `images.autoResize`, and model resize options. Rejected results are removed so a retry can succeed, and abort clears the cache. Returned images do not expose mutable cached image objects.

`node --test packages/pi-attachments/test/image-delivery.test.mjs` passes all 15 cases on unmodified Pi 1.0.2. These cases install the actual image module into Pi's native session with retained-file fixtures and a controlled provider; they do not load the complete attachment extension or composer. The original 11 cases cover effective resize overrides, required BMP conversion, supplied images, duplicate references, unchanged retained bytes, final blocking changed in either direction while queued, pre-queue failures with active work and prompt history preserved, and durable recovery with `--no-session`. Four additional cases prepare through a public fixture command before Send: concurrent and subsequent reuse with earlier input images, changed resize preference, changed model image limits, and failure propagation with retained contents and retry. The first reuse assertion failed before the method existed. Temporarily disabling cache reuse, omitting either effective-policy key, or retaining rejected results makes the corresponding regression fail; restoring the implementation passes. The earlier delivery-hook regression evidence remains valid for the public-input migration. Scoped image-module type, lint, formatting, and whitespace checks pass. Root typecheck still reports the remaining editor/Markdown/composer contracts; complete native-editor and composer acceptance belongs to ticket 07.

The caller must validate its frozen session before invoking `prepare`. Public input still saves its then-current transformed text and supplied images before reusing prepared image content, since other handlers can change them after the earlier preparation. This recovery write remains asynchronous. The cache adds no input scheduling and does not establish the pre-clear Send gate or same-route ordering; those remain ticket 04's integration work. The nine deferred delivery-time assertions remain explicitly skipped in ticket 06 and do not count among these passing cases.

**Ordering experiment — observed limits, not accepted behavior:** Run `node --test packages/pi-attachments/fixtures/image-input-ordering-experiment.mjs` explicitly. All five probes reproduce their recorded observations on unmodified Pi 1.0.2. The three image probes hold the first submitted image's file read, then submit later plain text. Normal UI input preserves the original order. During steering and follow-up, the later text enters Pi's queue first, then the image enters second when its read completes. The two controls reproduce the same overtaking with an ordinary asynchronous input handler and no attachments. Strict Send-order during streaming is therefore not established by the public input hook.

A package-owned promise chain at the input hook could delay later inputs until earlier image preparation finishes and preserve arrival order at this hook, but it could not recover order already changed by earlier asynchronous handlers. The accepted next experiment is ticket 04's gate before editor clearing: one Send waits for already-running capture and required image preparation, preserves the original request and route, and keeps later same-route text behind that image. Test both editors, other input handlers, failures, and later draft edits. Native reordering is not accepted behavior. The revised experiment remains unverified and must pass before the integrated submission contract is complete.

Those results covered settings overrides, original bytes, conversion, supplied images, recovery, and submission routes. They do not verify this public-input migration. Physical Ghostty interaction was not observed.
