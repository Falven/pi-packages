# 04: Verify asynchronous attachment editing on unmodified Pi

**What to build:** A pending attachment operation updates only its requesting draft while preserving the selected editor, later edits, caret, selection where supported, and native history. Establish that the package can provide this behavior without host changes before porting the complete Markdown flow.

**Blocked by:** None (can start immediately).

**Status:** in-progress — the pre-clear feasibility experiment passes 71 cases on unmodified Pi 1.0.2 with both editors, but a subsequent run-ending command transition fails with both. The package adapter and full capture integration remain to be ported and verified. Tickets 05 and 07 remain gated until the transition failure is resolved.

**Specification:** [Pi Attachments](../../../docs/specs/pi-attachments.md) and [Pi Composer](../../../docs/specs/pi-composer.md), including their applicable architecture decisions.

- [ ] Use public editor APIs first and identify the exact missing public capability before each private dependency. CustomEditor and setEditorComponent() provide replacement-editor support; they do not adapt an existing editor or preserve its state automatically.
- [ ] Preserve the selected editor and keep pi-composer optional. Any necessary private adapter stays inside the package, affects only that editor instance, preserves unhandled native input, and is cleaned up on reload. Use no silent editor replacement, global prototype patch, private queue modification, or Pi source change.
- [ ] Remove reliance on locally added native editor identity and range-transaction APIs. Keep the composer's existing package-owned draft identity and targeted edits, without presenting them as additions to Pi's editor contract.
- [ ] Preserve identity and history across ordinary edits, undo, prompt-history recall, and repeated identical drafts. Equal text alone cannot identify a draft. Reject stale changes after draft or session replacement; asynchronous whole-draft replacement and a parallel attachment history are not acceptable substitutes.
- [x] Run the compatibility experiment on unmodified Pi with the native editor and composer separately. Cover pending capture with typing, caret movement, selection and redo where the editor supports them, undo, prompt history, collapsed native pastes, source operations completing out of order, repeated identical drafts, session changes, and reload cleanup.
- [ ] Test delaying submission before Pi clears the editor. One press of Send waits for captures already running for that draft and required image preparation, updates the original request's references to retained snapshots, then submits that request through Pi's native path. Preserve later edits, caret/selection, undo/history, recovery, and the original normal, steering, or follow-up intent. Do not require a second Send or replay Enter against a newer draft.
- [ ] Within each delivery route, later text must not overtake an earlier image because of attachment preparation. Exercise both editors, earlier input transformations and handlers that consume input, prompt-history association, repeated identical requests, preparation failures, and active work finishing or starting while preparation waits. Preserve unrelated work and report exact failures before proposing another behavior change; native reordering is not acceptance.
- [x] Keep immediate capture and snapshot reuse throughout the experiment. Do not move capture to Send, add native editing features the selected editor lacks, or weaken existing composer transactions to make the experiment pass.
- [x] Reuse the existing editor and session verification boundary with unmodified dependencies. The experiment may exercise the editor integration independently of unfinished settings and action migrations; passing it does not establish full-extension startup.
- [ ] If the experiment fails, record the exact failing behavior in this ticket and discuss any necessary behavior change before proceeding. A composer-only success or a modified-host success cannot satisfy this gate or unblock tickets 05 and 07.

**Integration:** Ticket 05 uses the proven editor integration for the complete capture flow. Ticket 07 verifies the integrated extension and actual restored installation. Record compatibility evidence and identified private API gaps here rather than in a separate report.

**Historical verification (2026-10-14):** The previous implementation passed 76 focused identity, recovery, composition, and cleanup checks and 28 chat relationship tests against the modified host, plus type, lint, and format checks. It depended on host-provided opaque identity and targeted transactions, so it does not prove this adapter feasible. Native selection and redo were unavailable in that verification; composer checks covered them. Physical terminal interaction was not observed.

**Compatibility experiment (2026-10-14):** Fresh dependencies from the frozen lockfile supplied unmodified Pi 1.0.2. Run `node --test packages/pi-attachments/fixtures/editor-submission-experiment.mjs` to reproduce the [focused experiment](../../../packages/pi-attachments/fixtures/editor-submission-experiment.mjs). It deliberately retains the failing assertions: six cases run, four controls pass, and the native-editor and composer normal-submission cases fail. The experiment loads the selected editor and a small observing extension through the existing editor/session/provider fixture; it does not load the unfinished attachment extension or replace the selected editor. It exercises actual native dispatch against the controlled provider.

The probe observes two distinct terminal submissions with identical Markdown, identified as `draft-1` and `draft-2`. An earlier asynchronous input handler consumes `draft-1` by returning `handled`. Attachment-side input observation sees only `draft-2`, whose text is indistinguishable from `draft-1`. Both editor callbacks retain their distinct package-owned asynchronous scopes, but the later normal input event has no originating scope or editor identity. Its expected `draft-2` identity is `undefined`. Each host sends exactly one accepted request, as native dispatch requires.

Normal submission clears the native editor before invoking `onSubmit`, then crosses the interactive host's pending-input promise boundary before reaching the public input hooks. An asynchronous scope around the editor callback does not cross that boundary. A FIFO of editor submissions would select the consumed first draft for the accepted second input; matching their equal text cannot repair the association. An earlier input handler may also transform the text or stop propagation, so the package cannot require itself to run first. This disproves asynchronous scope plus FIFO or text matching as a safe submission adapter; it does not prove that every possible editor adapter is impossible.

Steering and follow-up are controls for both editors. Their host paths invoke the session directly from the editor's input handling, and the accepted input retains `draft-2` through the earlier asynchronous handler. The four passing controls establish only that scoped identity survives those routes. They do not satisfy normal submission, asynchronous capture ordering, or the complete attachment contract.

Read-only source comparison found six relevant portions byte-identical between Pi 1.0.2 and restoration target `6fb2e7815` (1.1.0): native editor submission, normal interactive submission routing, the interactive run loop, the pending-input promise, public input event/result types, and the public editor interface. This supports the same submission-boundary limitation at the restoration target; it is not a runtime verification of Pi 1.1.0.

The public/private boundary is now clearer:

- The existing editor can be found through the public TUI component tree supplied to `setWidget()`. Replacement through `setEditorComponent()` is unnecessary for the probe and would not preserve the native editor's state automatically.
- Public text access, insertion, callbacks, and history insertion do not supply draft identity or a targeted asynchronous range transaction. Native cursor state, paste contents, undo snapshots, and prompt-history restoration would need a scoped adapter before targeted edits could be accepted. None of those private mutation dependencies has been adopted or verified here.
- The composer's existing identity and targeted edits remain package-owned. Removing their locally added host `override` and callback dependencies is still pending; a composer-only implementation would not resolve the normal-submission boundary.
- Public input events have neither an originating editor identity nor notification that an earlier handler consumed another input. Access to native pending-message state is outside the approved adapter scope and has not been added.

**Accepted revised experiment:** Delay Send before Pi clears the editor. Wait for capture already started for the requesting draft and required image preparation, replace its destinations with retained snapshots, and forward the original request through native submission. Preserve subsequent edits and the original normal, steering, or follow-up intent. One press suffices; requiring another Send or replaying Enter against a newer draft is not accepted. The earlier asynchronous-scope experiment does not establish that this pre-clear approach is impossible.

Extend that experiment to preserve Send order within each route: later text cannot overtake an earlier image because of attachment preparation. Verify native editor and composer separately with other input handlers, preparation failures, recovery, and changes to the active run during the delay. The ordering observations in ticket 01 are counterexamples to fix, not permission to accept reordering. No Pi source change or private queue modification may supply the missing behavior.

**Pre-clear feasibility verification (2026-10-14):** Run `node --test packages/pi-attachments/fixtures/editor-send-wait-experiment.mjs`. All 71 cases pass with zero failures or skips on frozen, unmodified Pi 1.0.2 dependencies; an independent run also passed all 71 cases. The [runner](../../../packages/pi-attachments/fixtures/editor-send-wait-experiment.mjs) loads the [instance-scoped probe](../../../packages/pi-attachments/fixtures/preclear-probe.mjs) and the selected native editor or composer through the real editor/session/provider fixture. It reuses attachment snapshot/recovery helpers and the actual image preparation and preview module. The production attachment entry point remains outside this experiment. The earlier six-case post-clear experiment retains its two failures; those failures are evidence against that approach, not skipped or passing acceptance cases.

The tested boundary captures Markdown on draft entry, freezes the request before clearing, waits for its existing captures and required image preparation, then invokes the native submission delegate with the prepared original text. Later typing or replacement remains in the selected editor. Steering and follow-up wait through completion of native input processing, including earlier asynchronous handlers and the image module's recovery writes. Originally normal requests wait for public `ctx.isIdle()` before native dispatch; Pi's normal interactive loop then preserves ordering. Native queues are never read or modified. The only composer change extracts its existing clear-and-submit operation into a package-owned `submitDraft()` method so the adapter can delay before clear.

The 71 cases cover:

- Native editor and composer separately: one Send, later typing, caret, undo, snapshot reuse after source changes, prompt-history return, distinct identical drafts, out-of-order captures, session changes, reload, and durable recovery with the original session attribution. Composer also retains its existing selection and redo; native selection and redo are not added.
- Normal, steering, and follow-up routes separately: later text waits behind image preparation and an earlier asynchronous input handler; transformed text and existing supplied images survive; consuming the first of two identical requests does not misassociate the second; preparation failure preserves recovery and allows the later request. An active run can end while capture waits, and unrelated work can start while an originally normal request waits.
- Actual collapsed native paste markers, asserted before editing: destination wholly inside a paste, crossing its typed tail, and crossing a second paste. Targeted replacement preserves expanded text, later typing, and raw/expanded undo.
- Path-loaded extension modules with distinct reload instances: native only, attachment integration before composer, and attachment integration after composer, both ordinary reload and first enablement during reload. Capture occurs before first preview with images hidden. Forced redraws, resize, and later typing reuse one snapshot. Public editor recreation, extension-created instance reuse, and `setEditorComponent(undefined)` restoration to Pi's built-in editor all remain usable.
- Native and non-overlay custom dialogs, including an unrelated draft replacement while a dialog is open. Pending capture never edits the replacement. Native custom-dialog restoration returns to the recorded original draft and reuses its snapshot instead of recapturing changed source contents.
- Manual compaction and asynchronous `session_compact` handlers: normal Send resumes after both finish. Typed exact `/reload` reaches native cleanup while capture is pending. `/reload` with arguments, unknown slash text, and skill-like text remain ordered; streaming follow-up treats literal `/reload` as message text while the run stays active.

The experiment exposed and corrected three concrete failures. Releasing an originally normal request during a new run reclassified it as steering; waiting on public idle state fixed this. Waiting only for `agent_settled` stranded normal Send after successful manual compaction, which emits no such event; a cancellable 50 ms public-idle recheck fixed this and still waits for asynchronous compaction handlers. Non-overlay custom-dialog restoration overwrote the completed snapshot link with its saved source link and captured changed bytes a second time; associating the same-stack native restoration with the recorded editor and draft identity fixed it without changing native replacement behavior. A blanket Send gate also trapped `/reload`; only the exact native reload command bypasses preparation where native dispatch treats it as a command.

Verified public/private boundaries for production extraction:

- Public widget factories expose the TUI component tree, but there is no live-editor accessor or editor-replacement subscription. `getEditorComponent()` is public and returns a factory, not the selected instance. The probe discovers the live prompt and scopes an `addChild` wrapper to its containing instance. A widget render only schedules a guarded discovery microtask; all observation, capture, and mutation occur afterward. This covers reload's temporary box and stops retrying once installed. Reused instances must be reattached after native callback wiring. Temporary dialog editors are excluded. Cleanup restores instance methods and callbacks.
- Public text insertion cannot replace an expanded range while retaining native collapsed pastes, caret, and undo. The native adapter reads `state.lines`, `cursorLine`, `cursorCol`, and `pastes`; targeted edits use `pushUndoSnapshot`, `cancelAutocomplete`, `exitHistoryBrowsing`, `lastAction`, and `setCursorCol`. Existing paste IDs and the paste counter survive. Composer uses its existing package-owned range transaction instead.
- Public editor callbacks do not identify a draft or an undo/history restoration. A UUID-valued enumerable state field survives native structured cloning into undo snapshots and the saved prompt-history draft. Instance wrappers around `undo`, `undoStack.pop`, and `navigateHistory` preserve that token on restoration and assign a distinct token on replacement or another history entry. Tokens remain unique across reload. No text equality identifies drafts. Production must intern tokens as objects for the existing Markdown `WeakMap` and retain only attachment occurrence data, rather than copying the probe's full-text registry.
- Public submission callbacks run after native clearing. The native adapter therefore wraps that instance's `submitValue`; composer supplies its own pre-clear `submitDraft`. The native follow-up action is obtained from that editor's `actionHandlers` map. An asynchronous dispatch scope supplies the frozen expanded text for the follow-up read and prevents the native clear from erasing later edits. Native callback completion supplies streaming order; public idle checks and the native normal loop supply normal order. No identity must cross the failed post-clear pending-input boundary.
- Non-overlay custom dialogs save text and restore it after reinserting the editor. Public `ui_prompt_start`/`ui_prompt_end`, the recorded editor/draft identity, and a same-stack `setText` guard identify that restoration. Ordinary replacement drafts remain independent. This scoped restoration must remain separate from general draft replacement.

**Remaining implementation and validation:** Extract the verified adapter into the package, remove the modified-host contracts, and connect the actual Markdown registry, manual file/clipboard capture, Restore Inline, and image preparation. Already-running manual captures can exist before a Markdown link or any text exists; their requesting identity and insertion range must participate in the same pre-clear wait. The adapter should expose an expanded draft snapshot with object identity and insertion range, a targeted edit handle, and an attachment-only mutation scope. Index owns manual captures and combines preparation; Markdown owns its existing weak registry and destination rewriting. Do not carry the probe's second full-text history or duplicate capture/preparation implementation into production.

The passing matrix does not establish integrated startup, physical terminal graphics, or the restored Pi 1.1.0 runtime. Duplicate or ambiguous native paste markers need safe production handling; the probe rejects ambiguous mapping.

**Outstanding transition failure:** Subsequent checks fail with both the native editor and composer when a first follow-up waits for image preparation, a second follow-up contains literal `/reload`, and the original run ends before preparation fails or releases. The native idle follow-up fallback invokes normal submission, reloads the session, and never delivers the literal message. The 71-case checkpoint covers `/reload` while the original run remains active; it does not cover this failure. Both reproductions are under investigation, and the delivery-intent and ordering criteria remain unchecked. Tickets 05 and 07 stay gated; no behavior change or production workaround is accepted by recording this evidence.
